## 停止②（構造化レビュー）で見つかり、同じ PR で直したこと

テストは全部緑（unit・統合・E2E・CI）のままで、実装を**ドメインの目で読んで**初めて見えたもの。

1. **決定 6 の判断材料が事実と違っていた（AI の側の誤り）。** 停止①で「一覧に患者の情報を出さない。行から発注詳細を開けば分かる」と
   推薦したが、**発注の詳細ページは存在せず**、症例発注の一覧にも患者は出ておらず、患者の情報が画面に出るのは新規登録の入力フォームだけだった。
   人はその前提で承認していた。前提を訂正して決め直してもらい、症例発注の行に患者 ID とイニシャルを出す形（(b)）にした。
   見える人は増えない（既存の一覧 API が同じ情報を施設のメンバーに返している）。医師名・性別・術式名は出さない
2. **取り消し済みの短貸返却が、区別なく「返した物」として出ていた。** `loan_return_items.status` と `loan_returns.status` を見ていなかった。
   取り消しは「その返却の記録は誤りだった」＝実際には返していないかもしれないので、リコールで取りこぼす向きの誤り。落とさずに出して文字で明示した
3. **行ごとの「元へ」リンクが、最新 50 件より古い記録に届かなかった。** 一覧ページが取るのは最新 50 件だけ。
   リコールで調べるのはたいてい過去の記録。E2E は作ったばかりの記録で測るので緑だった。リンクをやめ、種別ごとの一覧へのリンクと断り書きにした。
   確実に辿る作り（詳細ページと ID 指定の取得）は issue #809
4. route のテストの「応答に患者が含まれない」は、`searchLotItems` をモックにした上で見ていたので**モックが返した値を見ているだけ**だった。
   「repository の結果に足しも引きもしない」「エラー本文に患者の情報があっても応答に出さない」に書き直した
