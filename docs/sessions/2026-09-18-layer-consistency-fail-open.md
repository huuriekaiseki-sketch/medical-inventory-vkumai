## 何が起きていたか

scenario 1 は「DB 側・API 側の両方から条件を取れているか」を件数の下限で見る **fail-open 防止**。
ところが件数を `console.log(n)` で出していたため、色が強制される環境では node が
`util.inspect` の色付きで数値を出す。

```
scripts/check-layer-consistency.test.sh: line 91: [: \e[33m61\e[39m: integer expression expected
scripts/check-layer-consistency.test.sh: line 93: [: \e[33m80\e[39m: integer expression expected
  OK: DB \e[33m61\e[39m 列 / API \e[33m80\e[39m 件を突き合わせる
```

`[ "$DB_COUNT" -lt 20 ]` が「integer expression expected」で非 0 を返し、`elif` も同じく落ち、
**`else` の `assert_ok` に到達して必ず OK を返す**。
C-022（緑であることと守っていることは別）そのもの。

## 02 内部でどう守っているか

**対策を 2 つ重ねた。**

1. **出す側で色を出さない**: `console.log(n)` → `process.stdout.write(String(n))`。
   `util.inspect` を通らないので色が付かない
2. **読めなかったら合格にしない**: `is_count`（`^[0-9]+$`）で検証し、数値でなければ
   `else` へ落とさず**その場で落とす**。混ざっていた値も `printf '%q'` で出す

> (1) だけだと、別の経路で色や余計な出力が混ざったときにまた黙る。**(2) が最後の砦。**

さらに検査自身の中に `scenario 0` を足し、「色付きの値を数値として通したら落ちる」ことを**毎回測る**。
再発すればここが落ちる。

### 同じ型が他に無いか

`console.log(Object.keys(...))` で件数を取り出している箇所を走査したところ、
`check-text-length-consistency.test.sh` に 1 件あった。ただしこちらは**数値ではなく文字列の連結**を
出しており `util.inspect` の色付けは掛からない。`FORCE_COLOR=1` で実測して問題ないことを確認した。

## 05 何かあったらどうするか
- 異常の判断基準: scenario 0 が落ちる → 数値の読み取りにまた色や余計な出力が混ざっている
- ロールバック: revert のみ

## 後任AIへの注意
- **シェルへ数値を渡すときは `console.log` を使わない。** `util.inspect` が色を付けうる。
  `process.stdout.write(String(n))` にする
- **`if/elif/else` の `else` を「正常」に使わない。** 比較が失敗したときも `else` に来る。
  読めなかった場合を**先に**判定して落とす
- `scenario 0` は消さない。これが無いと再発しても緑のまま
