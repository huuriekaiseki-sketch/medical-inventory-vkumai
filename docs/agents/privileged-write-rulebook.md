# RLS を通らない書き込み（W-xxx）

**`service_role` で書く経路 1 つ = 1 行。** `service_role` は RLS を通らないので、
**認可はアプリ側のガードにしか無い**。ガードを書き忘れても DB は止めてくれない。

RLS 経路（利用者の JWT）は文ごとに `is_facility_writer()` を評価し直すので、
権限を落とした次の文から効く。`service_role` 経路にはその再評価が無い。
だから「どの経路が、何を根拠に書いてよいことにしているか」をここに並べる。

- ロールごとの権限は [施設ロールの決めごと](./role-rulebook.md)（R-xxx）
- 失効までの時間の約束は [約束カタログ](./promise-catalog.md) の P-023
- 記録が残るかは [テーブルの決めごと](./table-rulebook.md)（TB-xxx）の監査の列

## 更新ルール

- 列は固定 8 列: ID / 経路 / 何を書くか / 認可の判定 / 判定から書くまで / 隙間に起きうること /
  守るテスト / 状態。列の中に `|` を書かない。
- ID は `W-` + 3 桁。区分ごとに 10 刻み（管理 API 01x / 記録の裏方 02x）。欠番は詰めない。
- **認可の判定**列には、実際にそのファイルで呼んでいる関数名をバッククォートで書く。
  機械がファイルの中身と突き合わせる（書いたのに呼んでいなければ落ちる）。
  判定を持たない経路は `無し` と書き、なぜ要らないかを「隙間に起きうること」に書く。
- 状態は 3 語のみ: 実装済み / 計画 / 対象外。

## 新しく `service_role` で書くときの手順

1. **この表に 1 行足す**。足さないと `src/__tests__/privileged-writes.test.ts` が
   「宣言が無い」で落ちる（`npm test` に含まれるので毎 PR）。
2. 認可の判定を書き、その関数名を「認可の判定」列に書く。
3. 「判定から書くまで」に何を挟むかを書く（本文の読み取り・外部呼び出し・複数の DB 往復）。
   ここが長いほど、判定の前提が変わる余地が大きい。

## この表から外れたもの

- **所属と役割の変更（旧 W-010）は 2026-09-07 に `service_role` をやめた。**
  `user_facilities` に `is_admin() AND has_aal2()` の書き込みポリシーを作り（20260907030000）、
  管理 API を利用者の JWT に切り替えた（P-035）。認可の再評価が書き込みと同じ文の中で起きるので、
  **窓が消え、権限の付け替えにも aal2 が要るようになった**。
  それまでは、マスタの書き込みには aal2 が要るのに（P-033）権限の付け替えには要らず、
  パスワードだけ奪われた admin が共犯者を admin に昇格させられる状態だった。
  **この表から行が減るのが、いちばん良い直り方**（窓を狭めるのではなく経路を無くす）。

## W-011 の限界と、いま守れているもの

**「しょうがない」で終わらせないために、制約・防御・未実施を書き分ける。**
どこまでが自分たちの責任で、どこからが外部サービスの制約かを説明できる状態にしておく。

### 消せない理由（外部サービスの制約）

1. **Supabase Auth の管理 API は `service_role` キーでしか呼べない。**
   利用者の作成・削除・招待は `auth` スキーマ（GoTrue の管理下）への操作で、
   アプリの RLS が及ばない。鍵を使わずに実行する方法が無い。
2. **DB の RLS トランザクションに統合できない。**
   PostgREST は複数文のトランザクションを提供しないので、「確認して、それから書く」を
   1 つのトランザクションに入れるには SECURITY DEFINER 関数に押し込むしかない。
   だが上記のとおり Auth の操作は SQL で書けないので、その手が使えない。
   P-035 で `user_facilities` にやった「経路そのものを無くす」は、ここでは選べない。

### いま守れているもの（実装済み）

3. **実行直前に admin と aal2 を再確認する。** `assertAdminAal2`（`src/lib/admin-auth.ts`）を
   Auth API を呼ぶ 1 行前で呼ぶ。ハンドラ先頭の `requireAdmin` に加えての 2 回目で、
   窓が「本文の読み取りを含む全体」から「再確認から Auth 呼び出しまで」に縮む。
   判定できないときは通さない（fail-closed）。**ゼロにはならない。**
   あわせて、マスタ（P-033）と権限の付け替え（P-035）が要求する aal2 を
   Auth の管理 API にも揃えた（ここだけ要求しないと迂回路になる）。
4. **拒否を記録する。** 再確認で弾いた分は `access_denials` に `aal2_required` として残る
   （20260907040000 で理由の語彙に追加）。異常な回数は `check_denial_anomalies` が拾う。
5. **所属と役割の変更は監査ログに残る。** `user_facilities` は監査対象（TB-030）で、
   P-035 以降は `actor_id` に「誰が権限を配ったか」も入る。

6. **特権操作の成功・失敗を記録する（2026-09-07 に追加）。** 招待・削除は成否によらず
   `privileged_operations`（TB-043・P-066）に 1 行残る。誰が・誰を・いつ・通ったか・失敗の code。
   招待は相手がまだ存在せず利用者 ID が無いので、**メールを残す**（人が決めた。読めるのは
   aal2 の admin だけで、サーバーログには伏せ字で出ない）。
   それまでは**弾かれた分だけが `access_denials` に残り、通った分は 1 件も残らない**
   非対称な状態だった（監査トリガーは `public` スキーマにしか付かず `auth.users` に届かないため）。

### 守れていないもの（未実施。隠さず書く）

7. **Studio や service role キーを直に使った `auth.users` の操作は記録されない。**
   `privileged_operations` に残るのは**このアプリの route を通った分だけ**
   （[blast-radius](./blast-radius.md) の B-010 と同じ範囲）。Supabase 側のログにはあるが未確認。
   → #757-28（データの残存先）と #757-35（本番設定の棚卸し）で扱う。
8. **Auth API の呼び出しと記録は同じトランザクションに入らない。**
   Auth は SQL の外なので「Auth は成功したが記録は失敗した」が起こりうる。
   記録の失敗で操作は止めない（記録だけ fail-open）ので、**取りこぼしはゼロにならない**。
   MFA の登録・解除、パスワード再設定はこの route を通らないので対象外。
9. **操作トークンや有効期限は無い。** 「この操作を N 分以内に実行してよい」という短命の
   トークンを発行して Auth 呼び出しに添える設計にすれば、窓はトークンの寿命に縛られる。
   いまは実装していない（判定と実行が同じリクエスト内なので、効果に対して複雑さが勝る）。
10. **失敗時の状態を検知して復旧する仕組みは無い。** 招待は送ったが所属を作れなかった、
   利用者は消したが `user_facilities` の行が残った、のような中間状態は
   [部分成功の棚卸し](./partial-success-inventory.md)（M-xxx）が扱う。
   現状は「次に同じ操作をすれば収束する」までで、**検知して自動で戻す仕組みは無い。**

### 読み方

**ゼロリスクではない。** ただし残っているのは (7)〜(10) の 4 つで、
そのうち (9) は選ばなかった設計、(7)(10) は別の番号で追っており、
(8) は外部サービスの制約そのもの（Auth と DB が同じトランザクションに入らない）。
「Supabase の制約だから何もしていない」ではなく、**制約の外側は塞いである**。
2026-09-07 に (6) が守れている側へ移った（成功した特権操作が 1 件も残っていなかった穴を塞いだ）。

## 読み方

- **隙間を消すことはできない。** 判定と書き込みを 1 つの文にまとめない限り、間には必ず時間がある。
  実測では、降格と同時に走らせた 12 本の RPC のうち 8 本が通った（窓は約 25 ms）。
  `supabase/__tests__/integration/permission-race.integration.test.ts` が測っている。
- **消せない代わりに、通った書き込みは必ず監査ログに残る。** 説明責任は隙間があっても崩れない。
  同テストがそれも測っている。
- **決定的に守れるのは「判定がコミットされた後に始めた書き込みは通らない」まで。**
  これは RLS 経路も RPC 経路も 24 本すべてで確認している。

## 限界

- **`service_role` の鍵を持つ側は、この表の外でも書ける。** 表に載るのはアプリのコードだけで、
  Supabase Studio・CLI・migration からの書き込みは対象外（そこは監査ログとスキーマドリフト検知が受ける）。
- **判定の「中身」は見ない。** `requireAdmin` を呼んでいることは機械が確かめるが、
  その判定が正しいかは見ない（そこは P-021 と admin 境界の統合テスト）。
- **隙間の大きさは測っていない経路がある。** 実測したのは RPC 経路だけで、
  管理 API（W-010 / W-011）の窓はリクエスト本文の読み取り時間に依存し、実測していない。
- **静的な走査なので、間接的に service_role クライアントを受け取る形は追えない。**
  クライアントを引数で渡し回すようになったら、この走査は当てにならなくなる。
