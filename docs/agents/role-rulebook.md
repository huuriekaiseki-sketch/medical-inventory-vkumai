# 施設ロールの決めごと（R-xxx）

**ロール 1 つ = 1 行。** 新しいロールを足すときに決めることを 1 枚にまとめた正本。

「どのロールが何をできるか」は **4 か所**に別々に書いてある。

| どこ | 何を決めているか |
| --- | --- |
| DB の CHECK（`user_facilities_role_check`） | 受け付けるロールの一覧 |
| `is_facility_writer()` | 施設の行を書けるロール |
| `is_admin()` | マスタを書けるロール |
| `src/hooks/useFacilityRole.ts` の `canWrite` | 画面が書き込み UI を出すロール |

4 つとも**許可リスト**（載っていないロールは何もできない）なので、新しいロールを足しても
勝手に権限が生えることは無い。**問題は互いに一致しているかを誰も見ていなかったこと**で、
viewer を足したときは TypeScript 側の更新漏れで誤表示が 2 回起きた（`src/types/role.ts` の WHY）。

さらに、新しいロールを足しても**そのロールを測るテストは 1 本も増えなかった**。
この表に 1 行足すと、上の 4 か所との一致と実 DB での実測が同時に要求される。

- 誰が何をできるかの**約束**は [約束カタログ](./promise-catalog.md)（P-020〜P-022）
- 表ごとの決めごとは [テーブルの決めごと](./table-rulebook.md)（TB-xxx）

## 更新ルール

- 列は固定 8 列: ID / ロール / 施設の行を読む / 施設の行を書く / マスタを書く / 画面の書き込み UI /
  守るテスト / 状態。列の中に `|` を書かない。
- ID は `R-` + 3 桁。区分は 01x（施設ロール）のみ。欠番は詰めない。
- 「読む」「書く」「マスタ」「画面」は **`はい` / `いいえ` の 2 語のみ**。
  機械が SQL・TypeScript の許可リストと突き合わせるので、曖昧な語を書かない。
- 守るテスト列はバッククォートでパスを書く。`実装済み` の行は必須。
- 状態は 3 語のみ: 実装済み / 計画 / 対象外。

## 新しいロールを足すときの手順

1. **この表に 1 行足す**（先に決める）。足さないと `role_registry.test.ts` が
   「宣言が無い」で落ちる（`npm test` に含まれるので毎 PR）。
2. migration で CHECK にロールを足す。書けるロールなら `is_facility_writer()`、
   マスタを書けるなら `is_admin()` も同じ migration で更新する。
3. `src/types/role.ts` の `FACILITY_ROLES` に足す。
   書き込み UI を出すなら `src/hooks/useFacilityRole.ts` の `canWrite` にも足す。
4. `supabase/__tests__/integration/role-capabilities.integration.test.ts` は
   **この表を読んで全ロールを実測する**ので、行を足せば自動で測定対象になる。
   実測が宣言と食い違えばそこで落ちる。

**4 か所のうち 1 つでも忘れると落ちる**（宣言と実態の両方向で突き合わせる）。

## 読み方

- **admin は施設をまたぐ。** `is_admin()` は所属施設を見ないので、admin は全施設の行を読み書きできる。
  到達範囲は [blast-radius.md](./blast-radius.md) の B-xxx が扱う。
- **「施設の行を読む」は所属している施設に限る**（admin を除く）。他施設は RLS で不可視。
- マスタの書き込みは admin であることに加えて `has_aal2()` も要る（P-033）。
  この表はロールの軸だけを見ており、MFA の軸は約束カタログが持つ。

## 限界

- **ロールの軸しか見ない。** 同じロールでも MFA（aal1 / aal2）・施設への所属の有無で結果は変わる。
  そこは P-030〜P-034 と RLS/IDOR のテストが担当で、この表では扱わない。
- **「はい / いいえ」の粒度しかない。** 「発注は書けるが価格は書けない」のような表ごとの
  細かい権限は表せない。そうした分け方が要るようになったら、この表の列ではなく
  [テーブルの決めごと](./table-rulebook.md)側に軸を足す。
- **許可リストの一致は見るが、許可リストが妥当かは見ない。** 「viewer が書けてよいか」は
  業務の判断であって、機械には決められない。
- **SQL とテキストで照合している。** `is_facility_writer()` の書き方を
  `role IN (...)` から別の形（`role <> 'viewer'` など）に変えると、走査が読めなくなって落ちる。
  落ちるのは安全側だが、書き方を変えるときは走査も直す必要がある。
