# 境界を代表値で測らない（property-testing）

不変条件カタログ（[`invariant-catalog.md`](./invariant-catalog.md)）の各行は「破る操作が拒否されること」で
確かめている。ただしその「破る操作」は**代表値 1〜2 点**（quantity 0、unit_price -1、201 文字）で、
それは「その 1 点で止まる」ことしか言っていない。**境界そのもの**は測っていない（issue #757 の 6）。

ここでは値を乱数で作り、「DB が受け入れる ⟺ カタログの条件を満たす」という**同値関係**を測る。

## なぜ乱数で作るか

端の値を自分で並べると、生成元がテストと同じになる。
[取りこぼし台帳](./escaped-defects.md)の独立性の表でいう「同源」で、
**私が思いつかなかった形は永久に出てこない**。

実際、導入した初回の実行で反例が出た。

| 反例 | 何だったか |
| --- | --- |
| `-5e-324`（負の最小非正規化数） | `unit_price` は `NUMERIC(12,2)` なので、scale より小さい負の値は `0.00` に丸めて格納される。DB は受け入れる |

これは**実装の欠陥ではなく、私が書いたプロパティの間違い**だった。
不変条件は「送った値」ではなく「**格納された値**」についての条件（カタログの I-012 も
「単価スナップショットは 0 以上」と書いてある）。`-1` を送って 23514 を見る代表値テストからは、
この取り違えは永久に出てこない。プロパティを直したうえで、
「丸めても負のままの大きさ（0.01 以上）は必ず 23514」を別の性質として足した。

## 使い方

```bash
npx vitest run --config vitest.integration.config.ts supabase/__tests__/integration/invariant-properties.integration.test.ts
```

`bash scripts/run-integration-tests.sh` にも含まれる（統合テストの一部なので、実 DB が要る）。

依存は `fast-check@4.9.0`（`devDependencies`、MIT、推移依存は `pure-rand` のみ）。
実行時コードには入らない。導入の判断は [`dependency-update-runbook.md`](./dependency-update-runbook.md) の手順。

## 書き方の決めごと

- **性質は「格納された値」について書く。** 送った値について書くと、DB の型変換・丸め・
  既定値を無視した式になり、上の `-5e-324` のような偽の失敗を生む。
- **止まった理由まで見る。** `error != null` では足りない。`23514` でなければ
  `src/lib/invariant-error.ts` の写像が効かず、利用者には「予期しないエラー」が出る。
- **両方の枝に届いたことを数える。** 生成が偏って片側しか通らなくても、テストは緑になる。
  それは「テストはあるが何も見ていない」状態そのものなので、各性質は
  `hits.accepted` / `hits.rejected` を数えて `toBeGreaterThan(0)` で固定する。
  この検知が効くことは、生成を片側に寄せて落ちることで確認してある（RED 方向）。
- **回数は絞る。** 1 回ごとに DB 往復が入る。既定 25 回。増やすほど網羅に近づくが、
  統合テスト全体の所要時間と引き換えになる。

## 限界（先に書いておく）

- **網羅ではなく抜き取り。** 25 回では `INTEGER` の 42 億通りのごく一部しか試さない。
  「通った」は「反例が見つからなかった」であって「存在しない」ではない。
- **seed を固定していない。** 走るたびに違う値を試すので、**同じ commit でも落ちたり落ちなかったり
  しうる**。落ちたときは出力の `seed` と `path` を控えること（`{ seed: 78456490, path: "4:1:0:0" }`
  の形で出る）。再現には `fc.assert(..., { seed, path })` を渡す。
  この揺れは [`check-flaky-tests.sh`](./test-matrix.md) から見るとフレーキーと区別がつかない。
- **条件が業務として正しいかは何も言わない。** 測っているのは「DB がカタログどおりに振る舞うか」だけ。
  「数量の上限は本当に無くてよいのか」のような問いは
  [`design-questions.md`](./design-questions.md)（作る前に人に聞く）側の担当。
- **DB より手前の経路は対象外。** 画面・API 層で先に弾いていても、ここは DB に直接届く経路で測る。
  「画面では入力できない」は防御ではない（API を直接叩けば通る）という前提に立っている。
- **カタログ 27 行のうち 3 行しか書いていない。** I-010 / I-012 / I-020 のみ。
  残りは引き金付き（下記）。**件数の少なさを健全さの証拠に読まないこと。**

## 写像の外にあるもの（意図的に固定してある）

`quantity` は `INTEGER` なので、`2147483648` は CHECK に届く前に型変換で落ちる。
返るのは `22003` 系であって `23514` ではない。`src/lib/invariant-error.ts` は 23514 だけを
利用者向けの一文に写像しているので、**この経路は「予期しないエラー」になる**。

直すのではなく「どこからが写像の外か」をテストで固定してある
（`I-010 INTEGER の範囲を超えた数量は 23514 では止まらない`）。
写像を広げるなら、まず「数量に業務上の上限を置くか」を人に聞くのが先
（[`design-questions.md`](./design-questions.md)）。上限を置けば CHECK に届く前に落ちる話ではなくなる。

## 起動の引き金

- 不変条件カタログに新しい `I-xxx` を足したとき（その行に境界があるなら 1 本書く）
- 既存の CHECK / トリガーの条件を変えたとき
- 列の型を変えたとき（`INTEGER` → `BIGINT`、`NUMERIC` の scale 変更など。上の丸めの話が変わる）

**機械では起動しない**（統合テストの一部として回るだけで、「書き忘れ」は検知されない）。
カタログの「守るテスト」列に書かないと
`scripts/check-invariant-catalog.test.sh` が気づかないので、書いたら必ず列に足す。
