# 規模の実測（performance-baseline）

「数万件になったら何が遅くなるか」を推測で書かず、ローカルで作って測った記録（issue #757 の 19）。
数字そのものより **増え方**（件数を倍にしたとき何倍になるか）を見る。線形より急なものが危ない。

## 測り方

```bash
supabase start
ORDERS=12000 bash scripts/measure-scale.sh      # 一覧・明細・施設削除の時間（#757-19）
ROWS=1000000 bash scripts/measure-ddl-lock.sh   # DDL が書き込みを止める時間（#757-18）
```

1 施設に症例発注を `ORDERS` 件、明細を `ORDERS × ITEMS_PER_ORDER`（既定 3）件作り、
一覧・明細・施設削除の時間を測って後片付けする。ローカル以外の Supabase には向けられない
（スクリプトが URL を検査する）。

**CI では回さない。** 時間がかかるうえ、しきい値テストは環境差で揺れて偽陽性の温床になる。
[`test-matrix.md`](./test-matrix.md) の「規模の実測」は節目（依存の major 更新・外部公開前・
索引やスキーマを変えたとき）に人が起動する。

## 実施記録

### 2026-09-07（初回。外部キーの索引を足す前と後）

同じマシン・同じローカル Supabase で、migration `20260907000003` の前後を測った。

| 発注 / 明細 | 一覧 50 件 | 明細 1 発注 | 施設削除（索引なし） | 施設削除（索引あり） |
| --- | --- | --- | --- | --- |
| 3,000 / 3,000 | 2 ms | 2 ms | 547 ms | — |
| 6,000 / 18,000 | 2 ms | 2 ms | 2,863 ms | 371 ms |
| 12,000 / 36,000 | 3 ms | 2 ms | **statement timeout（削除できない）** | 680 ms |
| 30,000 / 90,000 | 5 ms | 1 ms | 未測定 | 2,143 ms |

**分かったこと**

- **一覧は速い**。`(facility_id, created_at)` の複合索引が効いていて、30,000 件でも 5 ms。
  一覧が遅くなる心配より先に、削除が壊れていた。
- **施設削除が行数の二乗で重くなり、12,000 件で完全に失敗していた**。PostgreSQL は外部キーを
  作っても参照する側に索引を作らない。親を 1 行消すたびに子テーブルを全走査するため、
  CASCADE の総コストが二乗になる。「消せる」はずの施設が、ある程度使うと消せなくなっていた
  （#757 の 12 が規模で壊れていた）。
- **索引を足すと 12,000 件で 680 ms**。増え方も線形に戻った（12,000 → 30,000 で 3.2 倍）。
- 明細 1 件ぶんの取得は索引の有無で差が出なかった。件数が小さいうちは全走査でも速いので、
  **「今遅くないこと」は索引がある証拠にならない**。

**やったこと**: `supabase/migrations/20260907000003_add_foreign_key_indexes.sql` で索引 10 本を追加。
再発は `scripts/check-foreign-key-indexes.test.sh`（CI `hooks-test`）が止める。
この検査は実測の前に書いていなかったら見つからなかった `distributor_products.product_id` も拾った。

### 2026-09-08（監査ログの読み方。索引を足す前と後）

`audit_log` は全表の変更が 1 表に集まるので、この製品で**いちばん早く大きくなる**（Q-004）。
本物と同じ列・同じ索引の**複製表**を 20 万行（79 MB）作って測った
（`audit_log` は append-only で消せないため、本物には入れない）。

| 画面の問い合わせ | 足す前 | 足した後 |
| --- | --- | --- |
| 既定（絞り込みなし・新しい順・50 件） | Seq Scan **5,791 blocks** / 19.5 ms | Index Scan **5 blocks** / 0.03 ms |
| offset 100,000（`parsePagination` の上限） | Seq Scan + **ディスクへ 10 MB の外部整列** / 30.4 ms | Index Scan 3,135 blocks / 8.7 ms |
| 期間で絞る（直近 1 日） | Seq Scan 5,791 blocks / 12.9 ms | Index Scan **5 blocks** / 0.02 ms |
| 実行した人で絞る（一様なデータ） | Seq Scan 5,791 blocks / 7.9 ms | Index Scan 80 blocks / 0.15 ms |
| 実行した人で絞る（**古い側にしか居ない退職者**） | Seq Scan **5,792 blocks** / 5.9 ms | Index Scan **5 blocks** / 0.03 ms |
| 施設で絞る（既存の索引が効く） | Index Scan 32 blocks / 0.06 ms | 同じ |

**分かったこと**

- **LIMIT 50 でも毎回 表全体を読んでいた。** 既存の索引は
  `(facility_id, occurred_at DESC)` と `(table_name, row_id)` で、
  **施設で絞ったときにしか効かない**。画面の既定は絞り込み無しなので、常に全走査だった。
- **同じ形の 3 表のうち audit_log だけが穴だった。** `access_denials` と
  `privileged_operations` には最初から `(occurred_at DESC)` と `(actor_id, occurred_at DESC)` が
  あり、先に作った audit_log にだけ無い。**作った順で片方だけ抜けた**形。
- **一様なデータでは穴が見えにくい。** 「実行した人で絞る」は一様なら索引なしでも 7.9 ms で、
  索引を足しても計画器は `occurred_at` の索引で済ませた。差が出たのは
  **古い側にしか記録の無い退職者**を探したとき（5,792 blocks → 5 blocks）。
  *測り方を偏らせないと、要る索引が要らなく見える。*
- **深い位置（offset 100,000）は 20 万行の時点で既にディスクへこぼれていた**（外部整列 10 MB）。

**書きの代償も測った**: 同じ複製表への 2 万行の挿入が 90.8 ms → 125.6 ms（**+38%**、
1 行あたり約 +1.7 マイクロ秒）。1 回の変更で 1 行しか書かないので、読みが約 1,000 倍
（5,791 → 5 blocks）速くなる代わりとしては安い。

**足さなかったもの**: `(table_name, occurred_at DESC)`。一様な場合も古い側に偏った場合も、
計画器は既存の `(table_name, row_id)` の bitmap か `occurred_at` の索引を選び、
5〜19 blocks に収まった。**残る穴**は「大量にあり、かつ全部古い table_name」で、
その形が出たら足す。

**やったこと**: `supabase/migrations/20260908010000_add_audit_log_read_indexes.sql` で索引 2 本を追加。
再発は `scripts/check-append-only-log-indexes.test.sh`（CI `hooks-test`）が止める
（append-only の印＝`_immutable()` トリガーで記録表を機械的に見つけ、
`occurred_at` / `actor_id` の索引を要求する）。

### 2026-09-18（マイグレーションが書き込みを止める時間。#757-18）

`-- lock:` の注記は 23 件あるが、そこに書かれた「止まる / 止まらない」は**人が書いた見積もり**で、
一度も実測していなかった（`scripts/check-migration-lock-safety.test.sh` は注記の**有無**しか見ない）。
`bash scripts/measure-ddl-lock.sh` で測った。本物の業務表ではなく、
同じ形（主キー・施設 id・数値・テキスト）の使い捨ての複製表を使う。

**(1) 所要時間 = ロックを保持する時間**

| DDL | 1 万行 | 10 万行 | 100 万行 | 増え方 |
| --- | --- | --- | --- | --- |
| `CREATE INDEX` | 2.6 ms | 10.9 ms | 84.4 ms | 線形 |
| `CREATE INDEX CONCURRENTLY`（対照） | 3.1 ms | 14.5 ms | 111.6 ms | 線形。**素より 1.3 倍遅い** |
| `ADD CHECK`（NOT VALID 無し） | 1.3 ms | 3.7 ms | 24.4 ms | 線形 |
| `ADD CHECK NOT VALID`（対照） | 1.4 ms | 1.1 ms | 1.1 ms | **一定** |
| `ADD COLUMN NOT NULL DEFAULT 定数`（対照） | 1.0 ms | 0.9 ms | 1.1 ms | **一定** |
| `ADD COLUMN NOT NULL DEFAULT 揮発関数` | 9.5 ms | 84.9 ms | 691.6 ms | 線形。**いちばん重い** |
| `ALTER COLUMN SET NOT NULL` | 1.3 ms | 5.9 ms | 46.5 ms | 線形 |
| `ALTER COLUMN TYPE` | 5.5 ms | 32.3 ms | 368.2 ms | 線形 |

**(2) 書き込みが止まるか**（100 万行。時間ではなくエラーコードで判定）

| DDL | 判定 |
| --- | --- |
| `CREATE INDEX` | **止まる** |
| `CREATE INDEX CONCURRENTLY`（対照） | 止まらない |
| `ADD CHECK`（NOT VALID 無し） | **止まる** |

**分かったこと**

- **注記の主張は実測と合っていた。** 「NOT VALID なら既存行を読まない」「定数の既定値つき列追加は
  書き換えを伴わない（PG11 以降）」は、**行数を 100 倍にしても時間が変わらない**ことで裏付けられた
  （1.1 ms のまま）。「止まる」と書いた側も線形に伸びる。
- **止まる時間は行数に比例する。** 100 万行で `CREATE INDEX` が 84 ms なら、1 億行では 8 秒程度。
  `-- lock:` に時間を書くときは、**対象表の現在の行数から比例で見積もれる**。
- **`CONCURRENTLY` は素の `CREATE INDEX` より遅い**（1.3 倍）。止めない代わりに長くかかる。
  migration はトランザクション内で走るので、そもそもこの選択肢は使えない（本番では利用の少ない
  時間帯に当てるしかない、という結論は変わらない）。
- **いちばん危ないのは `ADD COLUMN ... DEFAULT <揮発関数>`。** `gen_random_uuid()` のような
  実行ごとに値が変わる既定値は表を全部書き直すので、同じ「列を足す」でも定数の 600 倍かかった
  （100 万行で 692 ms 対 1.1 ms）。**見た目がほとんど同じなのに桁が違う。**
- ここの数字はローカル（Docker の PostgreSQL 17.6・Apple Silicon）の目安。列の数や索引の本数で
  係数は変わるので、**読むのは絶対値ではなく増え方**。

**測り方でつまずいた 4 つ**（同じ罠を踏まないために残す。詳しくは
`scripts/measure-ddl-lock.sh` の先頭）

1. DDL を `pg_sleep` で保持して測った → 止めていたのは DDL ではなく sleep。**4 種類とも「止まる」と
   出た**（C-023。手前の別の要因が結果を決めている）
2. 書き手を `DO` ブロックで書いた → `DO` は**単一トランザクション**なので書き手が先にロックを握り、
   DDL の側が 10 秒待たされていた（測る側と測られる側が逆）
3. 書き手を DDL の**後**に起動した → プロセスの起動順が結果を決め、`CREATE INDEX` が「止まらない」
   と出た（C-045）
4. `pg_stat_activity` が**トランザクション内でキャッシュされる**（PG15 以降）ことを知らず、
   待ちループが同じ古いスナップショットを見続けて DDL を一度も検知できなかった

**`lock_timeout` の値が判定を変える**: 200 ms にすると「DDL がそれより短ければ待ちきれて成功」
してしまい、ロックを取ったかどうかではなく**DDL の長さ**を見ることになる（`ADD CHECK` が
「止まらない」と出た）。1 ms にして初めて、時間と競合の有無を分けて測れた。

## 索引を足すときに止まるもの

`CREATE INDEX` は作成中その表への書き込みを止める。migration はトランザクション内で走るため
`CONCURRENTLY` が使えず、本番では利用の少ない時間帯に当てるしかない。
2026-09-07 の索引 10 本はローカル 36,000 行で約 40 ms だった。

**止まる時間は行数に比例する**ことを 2026-09-18 に実測した（上の節）。100 万行で `CREATE INDEX` が
84 ms なので、`-- lock:` に時間を書くときは**対象表の現在の行数から比例で見積もれる**。
「止まらない」と書いてよいのは、行数を 100 倍にしても時間が変わらないもの——
`NOT VALID` の CHECK と、**定数**の既定値つき列追加だけ（どちらも 1.1 ms のまま）。
既定値が `gen_random_uuid()` のような揮発関数だと表を全部書き直すので、
**同じ「列を足す」でも 600 倍かかる**。

書き込みを止める DDL を書いたら `-- lock:` の 1 行で「何がどれだけ止まるか」を残す
（`scripts/check-migration-lock-safety.test.sh` が注記の有無を機械検査する）。

### 2026-09-19（ロット検索。issue #803。索引を作らない判断の裏付け）

SPEC「今回やらないこと」: 中間一致では `lot` に btree 索引が効かないため、今回は migration を
作らず実データ規模で応答時間を 1 回測って記録する方針だった。1 施設に `case_order_items` を
12,000 件（うち検索対象のロットは最後の 1 件のみ、残りは全て別ロット）作り、
`searchLotItems` と同じ絞り込み（`case_orders!inner` で facility_id を明示条件にし、
`lot IS NOT NULL` かつ `ilike` で中間一致、`LIMIT 501`）を 5 回実行した。

| 発注明細の件数 | 応答時間（5 回） |
| --- | --- |
| 12,000 | 6.9 ms 〜 8.3 ms |

**分かったこと**: Seq Scan でも 12,000 件・1 施設分では実用上問題にならない速さだった
（施設ごとの発注件数がこの規模を大きく超えることは現状想定しにくい）。索引を作らない判断（`pg_trgm`
+ GIN の追加を見送る）はこの規模では裏付けられる。**まだ測っていない**: 施設 1 つに数万〜十万件が
入るケース、`loan_return_items` 側（同型のクエリなので同程度と見込むが未測定）、複数施設が同時に
検索する場合の同時実行性能。件数が大きく伸びたら再測定し、必要なら `pg_trgm` + GIN の追加を別 issue
で検討する。

## まだ測っていないもの

- 発注以外の一覧（返却・消耗品・仕入価格）と横断履歴 `listOrders`。同じ複合索引の形なので
  速いと見込んでいるが未測定
- 施設が多いとき（テナント数の増加）。今は 1 施設に大量データを入れる形でしか測っていない
- 監査ログの**保持期間**。読み方は 2026-09-08 に測ったが、`audit_log` は append-only で消す手段が無く、どこまで増えるかは「使い方次第」のまま。いつ消すかは未決（#757-28）
- 本番の実データ量。ここの数字はローカルの目安であって、本番の性能ではない
- **本物の業務表での DDL 所要時間**。2026-09-18 に測ったのは列 4 本の複製表で、
  係数は列の数・索引の本数・TOAST の有無で変わる。増え方（線形か一定か）は変わらないので
  見積もりには使えるが、絶対値をそのまま本番の秒数として読まないこと
