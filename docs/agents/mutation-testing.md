# テストの効き目を測る（mutation-testing）

テストが緑であることと、テストが守っていることは別。認可の判断が書かれた場所のコードを機械的に
壊し、既存のテストが気づくかを測る（issue #757 の 7）。

## なぜ要るか

このリポジトリでは「テストは緑なのに修正が効いていない」型の失敗が 5 回以上再発している。
テストは 1,900 件を超えているが、**それが本当に拒否条件を守っているかを測る手段が無かった**。

初回の計測（2026-09-07）で、次の 3 つがすぐ見つかった。どれも「テストがある」ように見えて、
実際には 1 つも守っていなかった。

| 見つかったもの | 何が起きていたか |
| --- | --- |
| `src/lib/security/access-denial.ts` のスコアが 0.00% | 単体テストが 1 本も無い。統合テストはあるが `npm test` から除外されており、毎 PR では守られていなかった |
| `requireAuth` の拒否記録と上限の分岐 | `guard` / `reason` の中身も、上限超過で止まることも検査されていなかった |
| `authGuardError` の 429 判定 | 上限超過を 401 に化けさせる変異が生き残った（「なぜ弾かれたか」が分からなくなる） |

## 使い方

```bash
npm run test:mutation
```

`stryker.config.json` の `mutate` に書いた**認可の判断が書かれた場所だけ**を対象にする。
全体に掛けると時間も情報量も割に合わない。対象を増やすときはこの表の理由と一緒に足す。

結果は `reports/mutation/index.html`（人が読む）と `reports/mutation/mutation.json`（機械可読）。
生き残った変異は「そのコードを壊してもテストが気づかない」場所なので、テストを足すか、
そもそも要らないコードとして消す。

## 生き残りの読み方（5 分類）

生き残りを全部「テストの穴」として扱うと、実装を写しただけのテストが増えて逆に効き目が下がる。
2026-09-07 の 2 回目の計測で 4 種類に分かれ、2026-09-08 に 5 つ目（E）が出た。
**A・B・E の 3 つを直す。**

| 分類 | 何を意味するか | どうするか | 例 |
| --- | --- | --- | --- |
| **A. 未カバー** | その行をどのテストも通っていない | 直す（最優先） | `assertAdminAal2` に単体テストが 1 本も無く 35 変異が未カバー |
| **B. 通っているが見ていない** | 通ってはいるが、結果の一部を誰も検査していない | 直す | `recordAccessDenial({ guard: 'admin', reason: 'not_admin' })` を `recordAccessDenial({})` にしても緑 |
| **C. 等価変異** | 書き換えても**観測できる振る舞いが変わらない**（外側の防御と重複している） | 直さない。理由をここに書く | `if (!row) return unmeasured` を消しても、外側の `catch` が同じ値を返す。**タイムアウトの代わりの値**（`() => ({ data: null, error: null })`）を `{}` にしても、呼び出し側が `!data` で同じ拒否へ倒れる |
| **D. 文言・生成オプション** | 殺すにはテストが実装の文字列をそのまま写すことになる | 直さない。理由をここに書く | `apiError('limit は 1〜200 の整数で…')` のメッセージ本文 |
| **E. 同語反復** | テストが**定数と定数を比べている**。値を見ているように読めるが、実装側を書き換えると期待値も一緒に動くので何も守っていない | 直す（**D と紛らわしいので注意**） | `expect(e.message).toBe(INVARIANT_VIOLATION_MESSAGE)`。定数を空文字にしても両辺が空になり通る |

**E は D に化ける。** 「文言は殺さない」と決めた D と見た目が同じなので、
「これは D だから残してよい」と読み飛ばしやすい。**違いは、テストが実装の値を参照しているか**。
参照していれば E（守っていない・直す）、テストに文字列を書いていれば D（守っている・残してよい）。
2026-09-08 に `invariant-error.ts` で 2 件出た。どちらも**その日に自分が書いたテスト**で、
「文言を確かめている」つもりだった。利用者に届く文字そのものをテストに書いて直した
（80.65% → 93.75%）。

**B が一番多く、一番危ない。** 「テストがある」ように見えるからで、2026-09-07 に見つかった
生き残り 53 件のうち 23 件が「拒否の記録の中身（`guard` / `reason` / `actorId` / `facilityId`）を
誰も見ていない」という同じ形だった。この語彙は `check_denial_anomalies`（夜間の異常検知）が
数えているので、静かに空文字へ化けると**拒否の並びから乗っ取りを読む仕組みごと死ぬ**。

## 限界（先に書いておく）

- **等価変異は 0 にできない。** 残る変異が全部「穴」だと思って追いかけると、実装を写しただけの
  テストが増える。上の C・D に当たるものは、下の表に理由を書いて残す。
- **殺せた＝正しい、ではない。** 変異を殺すテストは「その行が今の値であること」を固定するだけで、
  その値が業務として正しいかは何も言わない。値の妥当性は
  [`design-questions.md`](./design-questions.md)（作る前に人に聞く）側の担当。
- **対象は 13 ファイルだけ。** ここに無いコードの効き目は測っていない。スコアが 93% でも、
  それは**認可の判断が書かれた 13 ファイルの中の話**であって、リポジトリ全体の話ではない。
- **スコアは対象の集合と一組でしか読めない。** 対象を増やせば下がり、減らせば上がる。
  数字だけを前回と比べると、広げたのか緩めたのかが分からなくなる（2026-09-08 に実際に起きた）。
- **機械では起動しない**（下の「起動の引き金」）。CI に載せていないので、この文書の予定日を
  過ぎても誰も止めない。
- **単体テストの実行環境では通らない枝がある。** 環境変数が無いときの早期 return
  （`if (!db) return`）や Supabase クライアントの生成オプションは、モックしている以上
  観測できない。実 DB を使う統合テスト側の担当。

## 下限（break threshold）

`thresholds.break` を下回ると終了コード 1 になる。**同じ対象のままなら下げてはいけない。**
上がったら、その値の少し下まで引き上げて固定する（ratchet）。
**対象を増やして下がったときだけ**置き直してよい。そのときは
「広げる前の集合のスコア」も併記する（下の「なぜ 94 → 92 にしたのか」）。

| いつ | 全体 | 変えた理由 |
| --- | --- | --- |
| 2026-09-07（初回） | 62.46% | 初回計測。break は 70 に置いたので失敗した |
| 2026-09-07（1 回目の補強） | 76.19% | 拒否記録・requireAuth・authGuardError にテストを足した。break を 75 に引き上げ |
| 2026-09-07（2 回目の補強） | 95.80% | 下の「2026-09-07（2 回目）」参照。break を 94 に引き上げ |
| 2026-09-08（対象を 12 ファイルへ） | 92.87% | **対象を広げたので分母が変わった**。break を 92 に置き直した（下の「なぜ下げたのか」を読むこと） |

### なぜ 94 → 92 にしたのか（下げたのではなく、測る範囲を広げた）

**「break は下げてはいけない」は、対象ファイルが同じままのときの話。**
2026-09-08 に判断点を 2 つ足した（`judgment-timeout.ts`：判定の待ち時間の上限、
`privileged-operation.ts`：特権操作の記録）ので、対象が 10 → 12 ファイルになり分母が変わった。

**元の 10 ファイルだけで測ると 94.10%** で、break 94 は満たしている。
全体が 92.87% に下がったのは**新しい 2 ファイルの分**で、その残りは
クライアント生成オプション・タイムアウトの代わりの値・テスト用ヘルパ（C と D）だけ。

対象を広げるときは、**広げる前の集合のスコアも一緒に出す**こと。
それをしないと「下がった」のか「測る範囲が増えた」のかが区別できない。

### ファイル別（2026-09-08 夕方。対象 13 ファイル・全体 92.79%）

`invariant-error.ts`（未登録 JAN と業務ルール違反を利用者向けの文言へ写す場所）を対象に足した。
**広げる前の 12 ファイルだけなら 92.73%**（459/495 変異）で、全体 92.79%（489/527）との差は新しい 1 ファイルのぶん。

| ファイル | 前回 | 今回 | 残り | 残りの分類 |
| --- | --- | --- | --- | --- |
| `invariant-error.ts`（新） | — | **93.75%** | 1 | C（`if (!details)` の番人。`RegExp.exec(undefined)` は文字列に変換されるので、ガードの有無が観測できない） |
| `api-error.ts` | 94.12% | 90.48% | 2 | D 2 件（`logServerError('api', …)` の文脈名。`repositoryError` を足したので同じ形が 1 件増えた） |

**この回で直した分（分類 E）**: `invariant-error.ts` の文言 2 件が**同語反復**だった。
`expect(e.message).toBe(INVARIANT_VIOLATION_MESSAGE)` は定数と定数の比較なので、
定数を空文字に書き換えても通る。あわせて「null を渡す経路」「コードを見ずに制約名だけで判断する変異」
「DETAIL の形が違う場合」の 3 つが未カバーだった（どれも B）。

## 起動の引き金

**機械では起動しない**（人が `npm run test:mutation` を打つ）。CI に載せていないのは、
1 回 2 分かかるうえ Actions の無料枠を使い切るため（issue #757 の 6 で有料化を判断するまで保留）。
代わりに定期作業として `scripts/maintenance-digest.sh` に載せ、下の予定日で期限を出す。

この「人が打つ」性質は [`undetectable-rules-inventory.md`](./undetectable-rules-inventory.md)
の扱いと同じで、**破られても機械では気づけない**。期限の管理だけが担保になる。
