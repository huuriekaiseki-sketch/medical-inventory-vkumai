# 上限（クォータ）の棚卸し（Q-xxx）

正規の権限を持つ 1 人が、その権限のまま**大量に**使ったときに何が起きるかを経路ごとに並べた表
（issue #757 の 32）。攻撃者ではなく、**権限のある人**が想定外の量を使う場合を扱う。
到達範囲の表 blast-radius.md（B-xxx、issue #757 の 39）が「どこまで届くか」を扱うのに対し、ここは「どれだけ使えるか」。

守るのは 3 つ。**お金**（外部サービスの従量課金）・**可用性**（他の利用者が使えなくなる）・
**他施設への影響**（1 施設の使い方が別施設に及ぶ）。

## 更新ルール

- 列は固定 6 列: ID / 経路 / 1 人がいまできること / 効いている上限 / 守るテスト / 状態。列の中に `|` を書かない。
- ID は `Q-` + 3 桁。区分ごとに 10 刻み（読み取り 00x / 書き込み 01x / 外部への送信 02x / 管理操作 03x）。欠番は詰めない。
- 状態は 4 語のみ: 上限あり / 上限なし（意図） / 要設定 / 未測定。
- 状態が 上限あり の行は、守るテスト列にパスを書く（`未` は不可）。
- 状態が 要設定 / 未測定 の行は `#757-N` を必ず書く（やらない理由か、いつやるかを残す）。
- 形は `scripts/lib/catalog-registry.json` に登録し、`scripts/check-catalogs.test.sh`（CI `hooks-test`）が検査する。
- **更新の引き金**: 外部サービスを使う機能を足したとき（メール・ストレージ・AI）、料金体系が変わったとき、
  実施設の利用が始まったとき、1 施設あたりのデータ量が桁で増えたとき。

## 読み方

- **いま本当に効いている上限は 4 つだけ**（Q-001 の件数、Q-003 のページ、Q-010 の冪等鍵、Q-012 の UNIQUE）。
  どれも「1 回の大きさ」の上限で、**「何回やれるか」の上限は 1 つも無い**。
- 外に出ていくのは招待メール（Q-020）だけ。お金と評判に直結するので、上限を決めるならここから。
- Q-002（レート制限）と Q-020（メール）は、置き場所（Vercel・proxy・アプリ）と値を決める判断が要る。
  値を決めずに仕組みだけ入れても意味がないので、実施設の利用開始前に決める。
