# 上限（クォータ）の棚卸し（Q-xxx）

正規の権限を持つ 1 人が、その権限のまま**大量に**使ったときに何が起きるかを経路ごとに並べた表
（issue #757 の 32）。攻撃者ではなく、**権限のある人**が想定外の量を使う場合を扱う。
到達範囲の表 blast-radius.md（B-xxx、issue #757 の 39）が「どこまで届くか」を扱うのに対し、ここは「どれだけ使えるか」。

守るのは 3 つ。**お金**（外部サービスの従量課金）・**可用性**（他の利用者が使えなくなる）・
**他施設への影響**（1 施設の使い方が別施設に及ぶ）。

## 更新ルール

- 列は固定 6 列: ID / 経路 / 1 人がいまできること / 効いている上限 / 守るテスト / 状態。列の中に `|` を書かない。
- ID は `Q-` + 3 桁。区分ごとに 10 刻み（読み取り 00x / 書き込み 01x / 外部への送信 02x / 管理操作 03x）。欠番は詰めない。
- 状態は 4 語のみ: 上限あり / 上限なし（意図） / 要設定 / 未測定。
- 状態が 上限あり の行は、守るテスト列にパスを書く（`未` は不可）。
- 状態が 要設定 / 未測定 の行は `#757-N` を必ず書く（やらない理由か、いつやるかを残す）。
- 形は `scripts/lib/catalog-registry.json` に登録し、`scripts/check-catalogs.test.sh`（CI `hooks-test`）が検査する。
- **更新の引き金**: 外部サービスを使う機能を足したとき（メール・ストレージ・AI）、料金体系が変わったとき、
  実施設の利用が始まったとき、1 施設あたりのデータ量が桁で増えたとき。

## 限界

- **上限があるかしか見ない。値が妥当かは見ない。** 毎分 300 回が適切かどうかは実運用の数字でしか
  決まらない。実施設が使い始めたら実データで見直す。
- **数え漏れは見つけられない。** 上限を通らない経路（新しい RPC、直接の PostgREST 呼び出し、
  外部サービス側の送信）は、この表に行を足さない限り存在しないことになる。
- **「1 回の大きさ」と「何回やれるか」は別。** 長さの上限（I-06x）が効いていても、
  回数の上限が無ければ量では守れない。逆も同じ。
- **外部サービス側の既定は見えない。** メール送信の実際の上限は Supabase の設定に依存し、
  ここからは確かめられない（#757-35 と同時に実測する）。

## 読み方

- **「1 回の大きさ」の上限**が 4 つ（Q-001 の件数、Q-003 のページ、Q-010 の冪等鍵、Q-012 の UNIQUE）、
  **「何回やれるか」の上限**が 2 つ（Q-002 の毎分 300 回、Q-020 の 1 日 50 通）。
  2026-09-07 まで後者は 1 つも無かった。
- 外に出ていくのは招待メール（Q-020）だけ。お金と評判に直結するので、ここは送る前に数える。
- **値は人が決めたもの**（毎分 300 回・1 日 50 通）で、実運用の数字ではない。
  実施設が使い始めたら実データで見直す（`aidd.config.json` の `decidedOn` が 2 年で期限切れになる）。
- 残る「未測定」は Q-004（監査ログの参照）だけ。全表の変更が 1 表に集まるので、いちばん早く大きくなる。
