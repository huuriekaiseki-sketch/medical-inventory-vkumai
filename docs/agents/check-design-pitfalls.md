# 検査の設計で間違えやすい型（C-xxx）

**検査そのものを設計するときの間違え方**を、値ではなく**型**で並べる。
ここに載っているのは全て、このリポジトリで**実際に起きて実測で確かめた**もので、
どれも「テストは緑のまま」「誰も困っていないように見える」形で潜んでいた。

他のルールブックとの境目:

- [`known-failure-patterns.md`](./known-failure-patterns.md) は**製品コードの**間違え方（1 件 = 1 節、長文）。
  こちらは**検査・仕組みの側の**間違え方を 1 行に圧縮したもの
- [`escaped-defects.md`](./escaped-defects.md) は「すり抜けた 1 件」の台帳。
  こちらはその 1 件から抜き出した**再発する型**
- [`undetectable-rules-inventory.md`](./undetectable-rules-inventory.md) は「機械で気づけないルール」の一覧。
  この表の 検知なし の行はそこにも載る

**値（閾値・バリデーションの中身・列名）はプロジェクトごとに違う。型は変わらない。**
別のリポジトリへ持って行くのはこの表であって、値ではない。

## 更新ルール

- 列は固定 8 列: ID / 間違え方 / どう現れるか / なぜ気づけないか / 設計での無くし方 / 実例 / 守るテスト / 状態。列の中に `|` を書かない。
- ID は `C-` + 3 桁。区分ごとに 10 刻み（宣言と実態のずれ 01x / 判定の弱さ 02x / 範囲と単位の取り違え 03x / 確かめ方そのものの誤り 04x / **道具の癖で結果が変わる 05x**）。欠番は詰めない（過去の PR 本文が ID を参照するため）。**1 区分は 10 個で埋まる**——04x が埋まったので 2026-09-11 に 05x を足した（シェルのパイプ・ランタイムの出力バッファのように、**書いた内容は正しいのに道具の都合で答えが変わる**型をここへ集める）。
- 状態は 2 語のみ: 検知あり / 検知なし。
- 状態が 検知あり の行は、守るテスト列にパスを書く（`未` は不可）。
- **実例は必ず日付と場所を書く。**「一般にありがち」で行を足さない。
  実際に起きて実測で確かめたものだけを載せる（思いつきで増やすと読まれなくなる）。
- 形は `scripts/lib/catalog-registry.json` に登録し、`scripts/check-catalogs.test.sh`（CI `hooks-test`）が検査する。
- **更新の引き金**: すり抜けが 1 件出たとき（`escaped-defects.md` に行を足すとき）に、
  **その 1 件が既存の型のどれかか、新しい型か**を必ず判断する。新しい型ならここに 1 行足す。
  既存の型なら実例に 1 つ足す（型が繰り返していることが分かるほうが重要）。

## 限界

- **型は思いついた範囲しか載らない。** 実際に起きて実測したものだけを載せる方針なので、
  まだ踏んでいない型はここに無い。ここに無いから安全、ではない
- **型に当てはめる作業は人がやる。** すり抜けが出たときに「これは C-020 だ」と判断するのは人で、
  その判断が漏れても機械は気づかない（`escaped-defects.md` の行が増えたときに見直す運用に依存する）
- **守るテスト列は、その型の実例 1 つを止める検査**であって、型そのものを全部止めるわけではない。
  たとえば C-010 の検査は攻撃表の `weak` 印しか見ておらず、他の場所にある別の「印」は見ていない
- **C-044 だけは機械検知を作らないと決めた（2026-09-10）。** 「`set -e` の下で外部コマンドの出力を
  素の `VAR="$(...)"` で受けている箇所」を走査することはできるが、**正常終了する前提のコマンド**
  （`mktemp -d` / `date` / `basename` など）が大量に当たるので、実用にならない。
  違反かどうかは「そのコマンドが失敗しうるか」で決まり、それは**呼び出し側の意図**であって
  静的には読めない。いまは型として記録し、**新しい検査を書くときに人が思い出す**ことに頼っている
- **C-032 の検査は 2 本に分かれている。** `scripts/check-rls-grant-gaps.test.sh` が
  「権限はあるが規則が無い」＝**アプリに道があって DB が誰にも許さない**側を、
  `scripts/check-write-path-gaps.test.sh` が逆向き＝**DB は許すのにアプリに道が無い**側を数える。
  逆向きは 2026-09-08（E-056）と 09（E-057）に 2 回、別々の表で見つかったので同日に足した。
  **どちらも「道があるか」しか見ない。** その道の認可が正しいかは攻撃表（P-017）の担当で、
  逆向きの検査は**隙間を件数で止めるだけ**（20 件の既存の隙間は宣言として残っている）
- **C-045 も機械検知を作らないと決めた（2026-09-11）。** 「時刻から決まる値を比較している検査」を
  静的に探すことはできるが、`Date` や `clock_timestamp()` を使う検査は正当なものが大多数で、
  **依存が悪さをするかどうかは「その値がいつ一致しうるか」**という中身の話になる。
  静的には読めない。**いまは型として記録し、時間に関わる検査を書くときに人が思い出す**ことに頼る。
  代わりに、落ちたときに「フレーキー」で片付けないことを運用で担保する
  （`scripts/check-flaky-tests.sh` → `scripts/lib/flaky-aggregate.mjs` は
  **揺れ（passed>0 かつ failed>0）と常時失敗（failed>0 かつ passed==0）を分けて出す**ので、
  再実行で消えた失敗も毎回落ちる失敗も一覧に残る）。
  **その担保が届く範囲（2026-09-12 に実測）**: 対象は **vitest のテストだけ**で、
  シェルの検査（`scripts/*.test.sh`・hook 回帰）は回らない。起動は
  `.github/workflows/flaky-detection.yml` の**週次 cron と手動実行だけ**なので、
  GitHub が使えない間は動かない（手元で同じスクリプトを打てるが、打つのは人）。
  **2026-09-12 の 2 件目はシェルの検査で、GitHub も停止中だった**——
  対象と起動の両方で担保の外にあり、一度も働かないまま 7 日後に赤くなった
- **C-046 も機械検知を作らないと決めた（2026-09-11）。** 「モックが投げる型」と
  「実物が投げる型」を突き合わせるには、`vi.mock` の差し替え先を辿って**実物の throw を
  静的に解析する**必要がある。分岐や再スローをまたぐと読み切れず、
  **読み切れなかったものを「一致」と読む検査**になりかねない（それは C-040 の型）。
  いまは型として記録し、**締めたときにモックが落ちたら実物を確かめる**運用に頼る。
  この 1 件は「締めたら落ちた」ことで見つかったので、**締める作業そのものが検知手段**でもある
- **C-048 も機械検知を作らないと決めた（2026-09-11）。** 「共通側のファイルに書かれた語が
  このリポジトリの固有名か、一般語か」は機械で判定できない。いまある禁止語の検査は
  **11 語のブラックリスト**（`plugin-layout.json` の `forbiddenWords`）で、
  ロール名・表名・閾値のように後から増えるものは列挙から漏れる。
  層の表から「アダプター側の資産名」を導いて禁止語に足す案も測ったが、
  **同じ語が release 文書・ひな形・fixture では正当に出る**（実測 14 ファイル）ので、
  誤検知のほうが多くなる。代わりに運用で置く——**共通側の仕組みを足したら、
  導入先を模した最小リポジトリ（名前を変えたもの）に当てて緑になることを一度測る**。
  2026-09-11 に見つかった 2 件（`codex-agents-sandbox.test.sh` と `canonical-event.ts`）は
  どちらも実体から導く形へ直したが、**残りを網羅的に探す手段は無い**。
  **2026-09-12 にこの運用を実際に回した**——導入先を模した 2 リポジトリ（別スタック）に
  配る検査を全数当て、根が導入先を向いていないものは 0 本と実測した（E-091 の調査の副産物）。
  ただし**これは実測であって門ではない**ので、次に共通側へ足す人が同じ測定をしなければ
  同じ形で戻る。運用に頼る型は「やったか」を機械で確かめられないという限界が残る
- **検知なしの型は C-044・C-045・C-046・C-048 の 4 つ。** 検知の無い型が出たときに
  ID を「## 限界」へ名指しで残すことは `scripts/check-pitfall-rulebook.test.sh` が強制する
  （名指しが無いまま「検知なし」と書くと落ちる）
- **C-022 の検知は、登録簿に書いた壊し方しか試さない**（`scripts/lib/check-mutants.json`、16 件）。
  別の壊し方なら生き残るかもしれない。判定エンジンを足したときに壊し方を足すのは人がやる
  （下限 `minMutants` が減るのを止めるだけ）。**生き残りが常に穴とは限らない**——
  別の道で落ちるだけの「同じ意味の変異」もある（CM-013 がそれで、落ちる文言まで見る形に強くして倒した）
- **C-022 の検知は、自分自身を壊しては測れない**（自分を壊して自分を走らせることになる）。
  代わりに `scripts/check-detectors-effective.test.sh` の scenario 2〜9 が、
  「生き残りを見逃さないか」「壊す前から赤いのを撃破と読まないか」を fixture で固定している
- **C-041 の検知は「全件を回したか」しか見ない。** 回した中身が十分かは見ない。
  セッションに 1 回しか鳴らないので、警告を見たあとにさらに触っても再度は鳴らない
- **C-030 の検知は E2E と統合テストの両方に入っている**（2026-09-09）。ただし
  **消してから作り直した**場合は鍵が同じなので気づけない。統合テスト側はさらに、
  **控えが 0 件の実行（`supabase db reset` の直後）では何も測っていない**
  ——出力にはそう書くが、止めはしない（E2E と違って 0 件が正しい状態でありうる）

## 読み方

- 新しい検査・仕組みを作る前に、まず **02x（判定の弱さ）** を読む。
  C-021（不在で判定するなら出る側の対を置く）と C-022（壊して落ちることを見る）は、
  この 2 つを守るだけで「緑だが効いていない」の大半が消える
- **C-023 は C-022 の先にある。** 壊して落ちることを確かめたのに落ちなかったら、
  「守れている」ではなく「手前の別の防御が止めていて、狙った防御を測れていない」を先に疑う
- **C-024 は C-022 の裏返し。** C-022 は「拒む向き」を測らない型で、C-024 は「通す向き」を測らない型。
  共有の部品を新しい対象へ付けたときは、両方向を動かして初めて「付いた」と言える
- いちばん危ないのは **C-012**。実害（aal1 の admin が全施設の金額を読める）が出た唯一の行で、
  発見も偶然だった（別の検査がたまたま落ちた）
- **C-030 と C-041 は同じ事故の表と裏**。片方だけ直しても再発するので、2026-09-09 に両方を機械化した。
  C-041 は「終える瞬間に全件を回したか」を聞き、C-030 は「回した結果、
  **走り出す前からあった行が消えていないか**」を見る。**後者が前者の中で効く**（全体で回して初めて分かる）
- **2026-09-09 に 検知なし はいったん 0 件になった**（いまは 4 件。上の「限界」で名指ししている
  C-044・C-045・C-046・C-048 で、いずれもその後に足した型）。**この行自体が腐っていた**——
  2026-09-12 まで「0 件になった」とだけ書いてあり、型が 4 つ増えたことが反映されていなかった。
  門（`check-pitfall-rulebook.test.sh`）が見るのは「検知なしの行が『## 限界』で名指しされているか」
  だけで、**文章の中身は見ない**ので、機械が見ない場所として静かにずれた。
  最後まで残っていた C-022 は
  「やったかどうかが痕跡に残らない」型だったので、痕跡を探すのをやめて**その場で壊して測る**形にした
  （`scripts/lib/check-mutants.json` に壊し方を宣言し、対応する検査が落ちるかを CI が毎回実測する）。
  検知が 0 件になったことは「もう間違えない」ではなく、**同じ間違い方をしたら機械が気づく**というだけ。
  新しい型は `escaped-defects.md` に行を足すたびに判断して増やす
