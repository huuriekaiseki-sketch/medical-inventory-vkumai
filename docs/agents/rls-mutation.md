# 認可そのものの効き目を測る（rls-mutation）

RLS ポリシーを 1 つ壊して、対応する統合テストが**本当に落ちるか**を実測する（issue #757 の 7）。

## なぜ要るか

2026-09-07 に TypeScript 層のテストの効き目を測ったら 62% だった（[mutation-testing](./mutation-testing.md)）。
ところが**認可の本体は RLS ポリシーにあり、そこは一度も測っていなかった**。
「RLS/IDOR のテストがある」ことと「RLS を壊したら落ちる」ことは別。

初回の計測で、**10 件中 4 件は誰も気づかなかった**（効き目 60%。TypeScript 層の初回とほぼ同じ）。

## 受け入れ条件

> 認可条件を 1 つ壊したら、対応するテストが少なくとも 1 つ失敗する。

アラート発火まで含める案もあったが、外部通知の経路が製品に無いので今回は対象外
（[security-test-catalog](./security-test-catalog.md) の B「検知できる」に残す）。

## 使い方

```bash
bash scripts/check-rls-mutation.sh
```

実 DB が要る（`supabase start` 済み）。1 件あたり 40 秒ほど（`supabase db reset` を挟むため）。**件数は `scripts/lib/rls-mutants.json` が正本**——ここには書かない（足すたびに古くなるので。C-010）。
1 件だけなら `bash scripts/check-rls-mutation.sh RM-002`（**部分実行は記録に残らない**）。

1 件あたりの流れは、壊す migration を置く → `supabase db push --local` → 対応するテストを回して
**落ちることを確かめる** → migration を消して `supabase db reset` で戻す。

`psql` と `supabase db execute` は hook が禁止しているので migration 経由で当てる。
戻すのに `db reset` を使うのは、**元のポリシー定義を書き写して戻すと、その写しがズレの発生源になる**から。
migration ファイルを唯一の正本のままにする。

### 生き残った 4 件（すべて本物の穴だった）

| 変異 | 気づかなかった理由 |
| --- | --- |
| RM-002 施設スコープの書き込みから aal2 を外す | aal2 のテストが **RPC 経由しか見ていなかった**。RPC は関数の中にも aal2 の判定を持つので、RLS 側を外しても落ちない。**表を直接叩く経路は RLS だけが守る** |
| RM-003 仕入価格の書き込みを閲覧者にも許す | 閲覧者のテストが消耗品と発注 RPC だけで、仕入価格を見ていなかった |
| RM-006 施設の作成から admin 判定を外す | マスタ境界のテストが商品・カテゴリ・代理店商品だけで、**施設だけ抜けていた** |
| RM-010 カウンタを認証済み利用者に開く | カウンタのテストが anon だけを見ていた。さらに**空の表を読んでいたので、漏れても 0 件が返って差が出なかった** |

RM-010 の 2 つ目は、この手の検査そのものの教訓になる。
**「読めないこと」を空の表で確かめても何も確かめていない。**必ず 1 行ある状態にしてから読む。

## 変異の増やし方

`scripts/lib/rls-mutants.json` に 1 件足す。

| 欄 | 何を書くか |
| --- | --- |
| `id` | `RM-` + 3 桁 |
| `breaks` | どの認可条件を、どう緩めるか |
| `sql` | `DROP POLICY` + 緩めた `CREATE POLICY`。表を新しく開く場合は `NOTIFY pgrst, 'reload schema';` を付ける（付けないと PostgREST 側に反映されず、変異が効かない） |
| `expect` | 落ちるべき統合テストのパス |
| `promise` | 対応する約束カタログの ID |

スクリプトは実行前に、ポリシー名とテストのパスが実在することを確かめる
（走査が壊れていると全部が「生き残り」に見えてしまうため）。

## 2 回目で分かったこと（2026-09-07）

**「admin 判定を外す」変異だけでは、aal2 の層が測れていなかった。**

初回の 10 件は「施設判定を外す」「admin 判定を外す」という*外側*の条件を壊すものばかりで、
`is_admin() AND has_aal2()` の **has_aal2() 側だけを外す**形が 1 件も無かった。
新しい表（`privileged_operations`）を足したときに気づき、同型のポリシーへ横展開したところ:

| 変異 | 結果 | 何が分かったか |
| --- | --- | --- |
| RM-011 `privileged_operations` | 生き残った | 招待先のメールを持つ表で、aal1 の admin が読めても誰も気づかない |
| RM-012 `access_denials` | 生き残った | 「MFA 登録済み・aal1 で読めないことは blast-radius が測る」とコメントに書いてあったが、**blast-radius はこの表を見ていなかった** |
| RM-013 `user_facilities` | 生き残った | **E-033 を塞いだ本体**。この migration の存在理由そのものが測れていなかった |
| RM-014 `products` | 倒せた | blast-radius の B-003 が測っていた |

3/4 が生き残った。**「aal2 を要求するポリシーを書いた」ことと「aal2 が効き続けることを測っている」ことは別**で、
前者だけやって後者をやっていない箇所が広く残っていた。

**もう 1 つ: RM-009 は等価変異だった。** 「価格履歴の直接 INSERT を許す」と書いてあるのに、
ポリシーだけ緩めても `GRANT SELECT` しか無いので INSERT は GRANT の段階で拒否される。
つまり**変異が自分の宣言を実装できておらず**、テスト側も 42501（GRANT レベルの拒否）を期待していたため、
**両方が「守っているのはポリシーだ」という同じ思い込みに乗っていた**。
GRANT INSERT も渡す形に直したら倒せた。
