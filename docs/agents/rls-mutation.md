# 認可そのものの効き目を測る（rls-mutation）

RLS ポリシーを 1 つ壊して、対応する統合テストが**本当に落ちるか**を実測する（issue #757 の 7）。

## なぜ要るか

2026-09-07 に TypeScript 層のテストの効き目を測ったら 62% だった（[mutation-testing](./mutation-testing.md)）。
ところが**認可の本体は RLS ポリシーにあり、そこは一度も測っていなかった**。
「RLS/IDOR のテストがある」ことと「RLS を壊したら落ちる」ことは別。

初回の計測で、**10 件中 4 件は誰も気づかなかった**（効き目 60%。TypeScript 層の初回とほぼ同じ）。

## 受け入れ条件

> 認可条件を 1 つ壊したら、対応するテストが少なくとも 1 つ失敗する。

アラート発火まで含める案もあったが、外部通知の経路が製品に無いので今回は対象外
（[security-test-catalog](./security-test-catalog.md) の B「検知できる」に残す）。

## 使い方

```bash
bash scripts/check-rls-mutation.sh
```

実 DB が要る（`supabase start` 済み）。全 10 件で 10 分ほど。1 件だけなら `bash scripts/check-rls-mutation.sh M-002`。

1 件あたりの流れは、壊す migration を置く → `supabase db push --local` → 対応するテストを回して
**落ちることを確かめる** → migration を消して `supabase db reset` で戻す。

`psql` と `supabase db execute` は hook が禁止しているので migration 経由で当てる。
戻すのに `db reset` を使うのは、**元のポリシー定義を書き写して戻すと、その写しがズレの発生源になる**から。
migration ファイルを唯一の正本のままにする。

## 初回計測（2026-09-07）

| 回 | 倒した | 生き残り | 何をしたか |
| --- | --- | --- | --- |
| 1 回目 | 6 / 10 | 4 | 初回計測 |
| 2 回目 | 8 / 10 | 2 | 閲覧者の仕入価格・施設の作成にテストを追加 |
| 3 回目 | **10 / 10** | 0 | 表への直接書き込みの aal2・カウンタの読み取りを追加 |

### 生き残った 4 件（すべて本物の穴だった）

| 変異 | 気づかなかった理由 |
| --- | --- |
| M-002 施設スコープの書き込みから aal2 を外す | aal2 のテストが **RPC 経由しか見ていなかった**。RPC は関数の中にも aal2 の判定を持つので、RLS 側を外しても落ちない。**表を直接叩く経路は RLS だけが守る** |
| M-003 仕入価格の書き込みを閲覧者にも許す | 閲覧者のテストが消耗品と発注 RPC だけで、仕入価格を見ていなかった |
| M-006 施設の作成から admin 判定を外す | マスタ境界のテストが商品・カテゴリ・代理店商品だけで、**施設だけ抜けていた** |
| M-010 カウンタを認証済み利用者に開く | カウンタのテストが anon だけを見ていた。さらに**空の表を読んでいたので、漏れても 0 件が返って差が出なかった** |

M-010 の 2 つ目は、この手の検査そのものの教訓になる。
**「読めないこと」を空の表で確かめても何も確かめていない。**必ず 1 行ある状態にしてから読む。

## 変異の増やし方

`scripts/lib/rls-mutants.json` に 1 件足す。

| 欄 | 何を書くか |
| --- | --- |
| `id` | `M-` + 3 桁 |
| `breaks` | どの認可条件を、どう緩めるか |
| `sql` | `DROP POLICY` + 緩めた `CREATE POLICY`。表を新しく開く場合は `NOTIFY pgrst, 'reload schema';` を付ける（付けないと PostgREST 側に反映されず、変異が効かない） |
| `expect` | 落ちるべき統合テストのパス |
| `promise` | 対応する約束カタログの ID |

スクリプトは実行前に、ポリシー名とテストのパスが実在することを確かめる
（走査が壊れていると全部が「生き残り」に見えてしまうため）。
