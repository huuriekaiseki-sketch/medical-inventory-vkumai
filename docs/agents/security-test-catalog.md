# 検査の引き出し（security-test-catalog）

**これはルーチンの一覧ではない。** 「こういう検査がある」を保存しておき、引き金が来たときに開ける引き出し。
毎回回すもの・変更時に回すものは [`test-matrix.md`](./test-matrix.md) が正本で、守る約束は
[`promise-catalog.md`](./promise-catalog.md)、着手順は issue #757。本ファイルはその外側にある観点を、
「いま要るか」「何が起きたら要るか」と一緒に置く。2026-09-06 に Codex のレビュー（7 回分、約 90 観点）を
整理して初版を作った。

## 枠組み

検査は次の **5 保証**のどれかに属する。個別項目を増やすより、機能ごとにこの 5 つが揃っているかを見る。

| 記号 | 保証 | 問い |
|---|---|---|
| A | 変更しても壊れない | 実装・設定・依存・モデルを変えたとき、拒否条件と不変条件がそのまま残るか |
| B | 検知できる | 侵害・誤操作・異常が起きたとき、人が気づく信号が出るか |
| C | 止められる | 危険な経路を、部分的に・即座に・波及させずに止められるか |
| D | 戻せる | 復元・ロールバック・鍵交換のあと、権限と証跡まで元に戻るか |
| E | 説明できる | 誰が・どの経路で・何を判断したかを後から第三者に示せるか |

機能ごとに揃えるのは **4 種類**: ①正常に動く ②攻撃されても拒否する ③障害時に安全側へ倒れる ④後から証明・停止・復旧できる。

## 状態の読み方

| 状態 | 意味 |
|---|---|
| 実装済み | 毎回か変更時に機械で回っている。守るテスト・hook・ratchet がある |
| 計画 #757-N | ロードマップの N 番として着手予定 |
| 引き金付き | いまは要らない。「引き金」列の出来事が起きたら開ける |
| 対象外 | この製品に該当する機能・条件が無い。理由を書く |

**引き金の書き方**: 機能の追加（決済・Webhook・ファイル受け取り）、事故、外部公開、利用者数の節目、
定期（月次 docs 差分・四半期訓練）のいずれかで書く。「いつか」は書かない。

## 引き金が引けない行（2026-09-12 の実測）

**引き金を「数」で書いた行は、その数を誰も数えていない。** つまり条件を満たしても気づけないので、
事実上引かれない（型は [`check-design-pitfalls.md`](./check-design-pitfalls.md) の C-010＝印だけがある状態）。
`scripts/lib/check-roadmap-staleness.mjs` が見るのは `計画 #757-N` の行だけで、
**「引き金付き」32 行と「対象外（現状）」5 行は 1 行も見ていない**ため、古くなっても誰も気づかない。

| 引き金 | 数える口 | 実測 |
| --- | --- | --- |
| 導入先が 3 リポジトリ以上 / plugin の導入先が 2 つ以上 | 無い | 導入先を記録した場所がリポジトリに無い。`MIGRATION.md` は手順書（riff-gear / cardiosearch は「**v0 は**手でコピーしていた」という過去形）、`CHANGELOG.md` の「導入先」は一般名詞、`evidence/` は中心リポジトリの受け入れ確認 1 本のみ |
| 施設数が 10 を超えたら / 利用施設が 2 つ以上になったら | 無い | 施設数を記録した場所が無い。[`quota-inventory.md`](./quota-inventory.md) は「実施設が使い始めたら実データで見直す」と書くだけ |

**直し方**: 数で引きたいなら、**数える口を先に作る**（実 DB の件数を夜間検査か統合テストで記録する、
導入先の一覧を文書に持つ、など）。**ただし「実 DB が要る」と決めつける前に、静的に再生できないかを
先に試す**——RLS ポリシーはそれで数えられた（下の「『数えられない』と書いて、数えられた例」）。
作れないなら、引き金を「数」ではなく
**機械で分かる出来事**へ書き換える——手本は「インポート／エクスポート境界」の行で、
「エクスポート機能が生えた瞬間に `scripts/check-export-paths.test.sh` が落ちる」と
**引き金に検査を紐づけてある**（この形なら、条件が満たされた瞬間に必ず気づく）。

**ここに一覧を置く理由**: 同じ注記を該当行へ 5 回書くと、次に直す人が片方だけ更新して必ずずれる
（2026-09-12 に `decisions.md` で同じ形を実際に作りかけた）。各行からはこの節を参照するだけにする。

### 「数えられない」と書いて、数えられた例（2026-09-13）

**この表に載せた 3 件のうち 1 件は、数えられないのではなく数え方を間違えていた。**
「RLS ポリシーが 30 本を超えたら」を 2026-09-12 に
**「静的には判定不能。現存数は実 DB の `pg_policies` が要る」**と書いたが、
翌日に migration を**順に再生**したら **35 本**と確定した。**閾値 30 はとっくに超えていた。**

当時の測り方は `CREATE POLICY` の出現回数（115）と `DROP POLICY`（95）を数えるだけで、
**順序を無視していた**。migration は連番で順序が確定し、このリポジトリでは `psql` /
`supabase db execute` が禁止で DB を変える手段は migration だけなので（経路外はスキーマドリフト検知が拾う）、
再生すれば現存集合は一意に決まる。動的 DDL（`DO $$ ... FOREACH t IN ARRAY ARRAY[...]`）も
表リストを読んで展開すれば数えられる——これを飛ばすと 4 行ぶん（20 文）が丸ごと落ちる。

**教訓は「1 つの測り方が駄目だったことを『測れない』と書かない」。**
調べ尽くした風の断定は、次に読む人の再挑戦を最も確実に止める。しかも「実 DB が要る」と書いたせいで、
上の**直し方の欄まで「夜間検査で記録する」と間違った方向**を指していた——人が Supabase を
起動しないと動かない検査に引き金を載せても、**上げ忘れた日は永久に引かれない**。

いまは `scripts/check-rls-policy-count.test.sh` が hook 回帰で毎回数える。
上限は `scripts/lib/rls-policy-budget.json` に**実測値 35 で張ってある**——30 で張ると
**初日から赤い検査**になり真っ先に無効化されるため。守るのは「これ以上増やさない」だけで
（`splittableMax` / `unclassifiedMax` と同じ帯）、30 超という事実は台帳の `_reviewTrigger` に
記録し、**検査の合否には使わない**（着手するかは人が決める）。

**残る 2 件は本当に数える口が無い**（導入先の数は記録した場所がリポジトリに無く、
施設数は実施設が使い始めるまで 0 が返るだけ）。
ただし**この 2 件も「測り方を 1 つしか試していない」状態でないかは疑うこと。**

### 検査を紐づけないと決めた行（2026-09-12）

**「機能が生えた瞬間に落ちる ratchet」は、その機能に固有で避けて通れない印があるときだけ作る。**
印が弱いまま作ると「検査はあるのに効かない」状態になり、**あること自体が安心の根拠に使われる**ぶん
無いより悪い（E-086 で実際に踏んだ形）。

| 判断した対象 | 紐づけない理由 |
| --- | --- |
| C 節「SSRF・クラウド metadata」の引き金（URL を受け取る機能） | エクスポートには `text/csv`・`Content-Disposition` という**避けて通れない印**があるが、外部 URL の取得には同等の印が無い。依存（`axios` 等）は走査できても、**標準の `fetch` に変数を渡す形**は正規表現では捕まえにくく、誤検知を避けるほど見逃しが増える（C-048 を却下したのと同じ構造）。代わりに**前提を実測で確かめた記録**を行に残し、次に読む人が「本当に URL を受け取っていないか」を同じ手順で測り直せるようにする |

**この判断は C-044 / C-045 / C-046 / C-048 と同じ扱い**（[`check-design-pitfalls.md`](./check-design-pitfalls.md) の「## 限界」）。
機械検知を作らないと決めた型は、**なぜ作らないかを書いて残す**——書かないと、次の人が
同じ検討を最初からやり直すか、印の弱い検査を作ってしまう。

### 前提を実測で確かめた行（2026-09-12）

**「まだその機能が無い」と書いた行は、本当に無いかを測ってから信じる。** 書いた日には正しくても、
機能が生えた日に行を直す人はいない。**測った印を残しておけば次の人が同じ手順で測り直せる**——
測り方の書いていない行は、結局もう一度ゼロから考えることになる。

| 判断した対象 | 測った印 | 結果 |
| --- | --- | --- |
| C 節「Archive slip・symlink・Git hook・submodule・巨大入力」の引き金 | `<input type="file">`、および `FormData` / `multipart` / `upload` | `type="file"` は **0 件**でファイル受け取りの UI が無い。`FormData` 等は 6 ファイルに出るが、いずれも通常のフォーム値の送信。**ヒット 6 件を「該当あり」と読めば誤り**だった |
| C 節「ターミナル制御文字」の引き金 | `scan-control-bytes.mjs` が見る 3 経路（`--files` / `--commits` / `--message`） | 既存の `check-control-bytes` は**追跡ファイルとコミットメッセージ**の ratchet で、**hook が実行時に組み立てる出力は対象外**。名前が近いだけの別経路なので「検査済み」とは書けない。C1 制御文字とゼロ幅文字も対象外（同ファイルの限界節） |
| C 節「通信の再構成差異」の引き金 | `next.config.ts` の `cdn` / `cloudflare` / `waf` | **0 件**。前段に CDN・WAF は置いていない |
| D 節「リプレイ・順序逆転」の引き金 | `src/` の `webhook` / `queue` / `cron` | ヒットは `src/lib/consumables/__tests__/repository.test.ts` **1 本だけ**で、中身は偽 DB ヘルパーの変数名（`makeDb(queues)` / `const queue = queues[table]`）。**本物の非同期処理は 1 つも無い** |

**印の強さは 4 つで違う。ratchet を作るかどうかはここで決まる**:

- **強い（作る）**: ファイル受け取り。`<input type="file">` と `request.formData()` の File 取り出しは
  **避けて通れない印**で、エクスポート境界の `text/csv`・`Content-Disposition` と同じ強さがある
- **弱い（作らない）**: 残り 3 つ。hook 出力の「外部由来の文字列」は書き方が無数にある。
  **CDN・WAF はそもそもリポジトリの外**（Cloudflare・Vercel のダッシュボード）で前段に入るので、
  ファイルをどれだけ見ても永久に分からない。Webhook も「外から POST される route」を
  静的に見分ける印が無い（session を見ない route は他にもある）

**4 つを同じ扱いにしないこと**が要点。印の弱い 3 つに ratchet を作れば、E-086 で踏んだ
「検査はあるのに効かない、しかも**あること自体が安心の根拠になる**」状態をまた作る。
