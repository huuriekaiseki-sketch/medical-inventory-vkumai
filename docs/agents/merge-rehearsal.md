# マージの予行演習（merge-rehearsal）

溜まったブランチを「この順で main へ入れたら衝突するか」を、**作業ツリーを触らずに**先に調べる手順。

## なぜ要るか

2026-09-06 に GitHub のアカウントが停止し、PR を出せないまま作業を続けた結果、ローカルに 22 本の
ブランチが溜まった。復旧後にまとめてマージする段になって初めて衝突が分かると、「どれを先に入れるか」
「どこを直すか」を大量に同時に判断することになる。衝突は**今**分かるので、今のうちに知っておく。

これは GitHub 停止に限らない。並行して 3 本以上のブランチを持つときはいつでも同じ問題が起きる。

## 使い方

```bash
bash scripts/rehearse-merge.sh                          # scripts/lib/merge-queue.json の順で
bash scripts/rehearse-merge.sh --branches feat/a,feat/b # その場で順番を指定
bash scripts/rehearse-merge.sh --json                   # 機械可読（CI 用）
```

衝突が 1 件でもあれば終了コードは 1。`git merge-tree` で木だけを計算し、成功したら `git commit-tree` で
仮コミットを積むので、**checkout も merge もしない**。作業中の変更は壊れない
（そのことは `scripts/rehearse-merge.test.sh` の scenario 3 が固定している）。

順番は `scripts/lib/merge-queue.json` に書く。マージが済んだブランチは消してよい（無いブランチは
「無し」として飛ばす）。依存があるもの（積み上げたブランチ）は後ろに置く。

**合流させる対象が 0 本なら合格ではない**（2026-09-11）。順番が空、または全部が「済み」か「無し」のとき、
終了コードは 4（**対象なし**）で、記録は `empty`。ハーネスの証拠の欄では「合格 ？」と出る（赤にも緑にもしない）。
それまでは全部が済みでも「衝突 0 件」で合格を記録しており、**次に本当の衝突が出るまで緑が続く**形だった（E-083）。
済みのブランチは `--prune-merged` で順番ファイルから外せる（無いブランチは済みとは限らないので残す）。

```bash
bash scripts/rehearse-merge.sh --base main --prune-merged   # 済みを順番ファイルから外す
```

## 読み方の注意（積み上げたブランチ）

衝突したブランチは**積まずに**次へ進む。そのため、衝突したブランチの上に積んだブランチも
「衝突」と出る（親の変更が土台に入っていないため）。実際には親を直せば子も通ることが多い。
親から順に直して、もう一度回すのが正しい使い方。

## 2026-09-07 の結果

24 本中 **10 本が衝突**した。中身はすべて「共有の表・設定に行を足した／状態を書き換えた」もので、
コードの衝突は 1 件も無かった。

| 衝突したファイル | 本数 | どのブランチ |
| --- | --- | --- |
| `docs/agents/test-matrix.md` | 3 | 31 fail-open / 19 索引と規模 / 18 ロック注記（19 の上） |
| `docs/agents/security-test-catalog.md` | 3 | 33 人間系 / 17 エクスポート / 38 部分成功 |
| `docs/agents/actuator-inventory.md` | 2 | 37 配布物の同一性 / 30 供給網の演習（37 の上） |
| `docs/agents/decisions.md` | 1 | 検査の配布 |
| `scripts/lib/plugin-layout.json` | 1 | マージ予行演習 |

このうち 18（19 の上）と 30（37 の上）は、親が衝突して積まれなかったことによる連鎖なので、
親を直せば消える見込み。実質の衝突は 8 件。

**分かったこと**: 並行作業のボトルネックはコードではなく**共有の 1 ファイルの表**だった。
1 行 1 件の表は、別々の行を触っていても行が隣り合っていれば衝突する。ブランチが増えるほど、
同じ表を触る確率が上がる。

**いまの対処**: 8 件はどれも「両方の行を残す」で解決できる軽いもの。順番どおりにマージし、
衝突したら両方を採用してから次へ進む。

**構造を変えるなら**: 表を 1 件 1 ファイルの断片にして生成物にすれば、ブランチ同士が同じファイルを
触らなくなる（ルールブックの索引 `rulebooks.md` で使った形と同じ）。並行ブランチが常時 5 本を
超えるようなら検討する。今回は一度きりの事情（アカウント停止）なので、そこまではやらない。

## 2026-09-07 夕方の結果（8 本を足して 32 本に）

先の 24 本に、表へ入れ忘れていた 8 本（20 入力の長さ・16 夜間チェック・5 ログ伏せ字・9 秘密走査・
10 ヘッダ・32 上限の棚卸し・作る前に聞く質問・32 回数の上限）を足して回した。
**32 本中 16 本が衝突**。増えた 6 件はすべて足したブランチ側で、内訳は前回と同じ性質だった。

| 衝突したファイル | 本数 | どのブランチ |
| --- | --- | --- |
| `docs/agents/test-matrix.md` | 7 | 31 fail-open / 19 索引と規模 / 18 ロック注記 / 16 夜間チェック / 5 ログ伏せ字 / 9 秘密走査 / 10 ヘッダ |
| `docs/agents/security-test-catalog.md` | 5 | 33 人間系 / 17 エクスポート / 38 部分成功 / 5 ログ伏せ字 / 9 秘密走査 |
| `scripts/lib/plugin-layout.json` | 3 | マージ予行演習 / 作る前に聞く質問 / 32 回数の上限 |
| `scripts/lib/derive-test-selection.rules.mjs` | 3 | 5 ログ伏せ字 / 9 秘密走査 / 10 ヘッダ |
| `docs/agents/actuator-inventory.md` | 2 | 37 配布物の同一性 / 30 供給網の演習 |
| `docs/agents/decisions.md` | 1 | 検査の配布 |
| `docs/agents/invariant-catalog.md` | 1 | 16 夜間チェック |
| `src/types/database.generated.ts` | 1 | 16 夜間チェック |
| `docs/agents/known-failure-patterns.md` | 1 | 5 ログ伏せ字 |
| `eslint.config.mjs` | 1 | 5 ログ伏せ字 |

**前回から変わったこと**: 衝突の 1 位は変わらず `test-matrix.md`（3 → 7 本）。
ブランチが 24 → 32 に増えただけで、同じ表を触る本数が倍以上になった。
「ブランチが増えるほど同じ表で衝突する」という前回の見立てが、そのまま数字に出た。

**コードの衝突が 2 件出た**（前回は 0 件）。`src/types/database.generated.ts` は生成物なので
マージ後に `supabase gen types typescript --local` で作り直せばよい。`eslint.config.mjs` は
規則を 1 つ足しただけなので両方を残す。残る 14 件は前回と同じ「両方の行を残す」で済む。

**判断**: 断片化（1 件 1 ファイル + 生成）の引き金に挙げた「並行ブランチが常時 5 本超」は
とっくに超えている（32 本）。ただし今回は一度きりの事情（アカウント停止）で溜まった分なので、
**この波を捌いてから**、次に同じことが起きるかどうかで決める。捌いた後も表の衝突が続くようなら
断片化に着手する。

## 2026-09-07 夜の結果（37 本）

依存を足す 3 本（テストの効き目の計測・画面の操作性・入口の入力検証）と拒否の異常検知・
監査ログの閲覧 UI を足して 37 本。**21 本が衝突**。

衝突の 1 位が `test-matrix.md`（7 本）から **`scripts/lib/plugin-layout.json`（8 本）** に変わった。
理由ははっきりしている。**新しい検査を作るたびに層の表へ 1 行足すから**で、この日は
検査を 5 本足した（設計時の答え・回数の上限・コントラスト・文字数の突合・拒否の網羅）。

`maintenance-digest.sh` とその構造テストの 3 本は、積み上げたブランチの連鎖
（上の「読み方の注意」参照）。親を先に入れれば消える。

**判断は変わらない**。層の表も 1 行 1 件の表なので、断片化すれば衝突は消える。
ただしこの波を捌くのが先で、捌いた後も同じ表で衝突が続くようなら着手する。

## 2026-09-07 の実行結果（40 本を main へ入れた）

**衝突を手で解く前に、衝突が起きない形にした。** 予行演習の 21 件は中身が全部「別々の行を足しただけ」
だったので、git に任せた。

| 段階 | 衝突 |
|---|---|
| 何もしない | 21 / 37 |
| `.gitattributes` に `merge=union`（追記型の表・文書 11 ファイル） | **14 / 37** |
| `merge=jsonunion`（キー辞書の JSON を構造で 3 者マージ） | 手で解いたのは **7 回だけ** |

union が効いたのは test-matrix・security-test-catalog・actuator-inventory・invariant-catalog・
decisions・known-failure-patterns。jsonunion が効いたのは plugin-layout.json（10 本ぶん）。

**手で解いた 7 回**は、どれも「両方の変更が必要」だった:
`admin-auth.ts`（fail-closed 化と拒否の記録）／`plugin-layout.json` 2 回（節ごと足した分）／
`eslint.config.mjs`・`derive-test-selection.rules.mjs` 3 回（隣接による偽の衝突）／
`maintenance-digest.sh` と `.test.sh`（定期作業が 3 → 7 本に増えた）／`db-schema.md`・`settings.json`。

**union の限界も実測どおり出た。** 衝突を報告しない代わりに、同じ行を両側が別々に書き換えると
両方が残る。実際に `I-052`（不変条件）と test-matrix の 3 行、catalog-registry の 2 エントリが
重複したが、**ID 重複・derive キー重複・limits 未記入の検査が全部捕まえた**。
機械側の受けがあれば union は安全に使える、という設計の裏が取れた。

**合流して初めて出た穴が 10 種類**あった（個々のブランチでは緑だった）。詳細は
`docs/agents/escaped-defects.md` の E-031 / E-032 と、コミット `0f3607b`。
特に版番号の衝突（`20260907000001` が 2 本）は `db reset` が止まって初めて分かる型で、
ファイル名の並びを見ているだけでは気づけない。

検証: 全 63 migration が素の DB に通り、`npm test` 226 files / 1877 件、
`run-integration-tests.sh` 35 files / 234 件、`scripts/*.test.sh` 97 本すべて緑。

**次に同じ波が来たら**: 先に `bash scripts/rehearse-merge.sh` で衝突を数え、
「両方の行を残す」で解けるファイルを `.gitattributes` に足してから並べる。
新しい clone・worktree では `bash scripts/setup-merge-drivers.sh` を 1 回実行する
（マージドライバの中身は git の仕様で配れない）。

## 更新の引き金

- 並行ブランチが 3 本を超えたとき（マージ前に 1 回回す）
- 長期のブランチを作るとき（週 1 回まわして、衝突が育つ前に気づく）
- 共有の表（カタログ・一覧）に列や節を足したとき（衝突の起きやすさが変わる）
