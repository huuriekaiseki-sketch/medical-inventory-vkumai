# 取りこぼし台帳（E-xxx）

**すり抜けた 1 件 = 1 行。** ルールブックに書いた「限界」が的外れかどうかは、書いた時点では分からない。
分かるのはテストやレビューで漏れが出たときだけなので、その漏れをここへ戻して限界とルールを育てる。

```
実装 → 検査 → 漏れが出る → ここに 1 行 → ルールブック・実装・テストを直す → 再検査 → 解決済み
```

**緑になっても終われない。** `未分類` の行が 1 つでもあると `npm test` が落ちる
（`scripts/lib/__tests__/escaped-defects.test.ts`）。実装を直して他が全部緑になっても、
分類していない漏れが残っている限りスイートは赤のまま。

- 落ちた検査は `scripts/record-test-failure.sh`（PostToolUse）が下書きとして
  `logs/escape-candidates.jsonl` に拾う。**判定はしない**（実装途中の RED は漏れではない）。
- 下書きを見ないまま終わろうとすると `scripts/check-escape-ledger.sh`（Stop）が聞く。
  該当なしなら `bash scripts/triage-escapes.sh --none "理由"` で記録する（黙って消す道は無い）。

## 更新ルール

- 列は固定 9 列: ID / 何が起きたか / 分類 / 何が見つけたか / 関連ルールブック / 誰が値を決めたか /
  直したこと / 再発防止 / 状態。列の中に `|` を書かない。
- ID は `E-` + 3 桁。区分ごとに 10 刻み（権限・認可 01x / 記録・監査 02x / 検査の運用 03x / 環境・道具 04x / 製品の振る舞い 05x / 検査の運用（続き）06x / 測定・評価の妥当性 07x）。**1 区分は 10 個で埋まる。** 03x が埋まったので 2026-09-08 に 06x を足し、06x が E-069 で埋まったので 2026-09-10 に 07x を足した（E-070 を書いたら「帯の外」で検査が落ちて気づいた）。
- **分類**は 4 語のみ: 実装バグ / テスト不足 / ルールブック不足 / 環境。
  `ルールブック不足` を選んだら、関連ルールブックの行と `## 限界` を直すまで `解決済み` にしない。
- **何が見つけたか**（検出源）は下の語彙から選ぶ。**独立性は検出源から決まる**ので行ごとに書かない。
- **誰が値を決めたか**: `domain_owner` / `security_review` / `product_owner` /
  `AI 提案（人が承認）` / `AI 提案（未承認）` / `該当なし`。
  上限・権限・保持期間・可視範囲のように**値を決めた**行では必須。
  `AI 提案（未承認）` が多い箇所は、ルール・実装・テストが同じ生成元に依存している合図。
- **再発防止**列にはバッククォートでパスを書く。`解決済み` の行はここが必須
  （`scripts/lib/check-catalog.mjs` が状態と突き合わせ、パスの実在も見る）。
- 状態は 4 語のみ: 未分類 / 対応中 / 解決済み / 該当なし。
- **1 件を直したら、それが「型」かどうかを判断する**（2026-09-09）。
  検査・仕組みの側の間違いなら [`check-design-pitfalls.md`](./check-design-pitfalls.md)（C-xxx）を見て、
  既存の型なら実例に 1 つ足し、新しい型なら 1 行足す（関連ルールブック列にその文書を書く）。
  **同じ型が繰り返していることが見えるほうが、1 件ずつ直すより効く。**

## 検出源と独立性

「独立」とは手段の名前ではなく、**ルール・実装・テストと別の前提から来ているか**で決まる。
DB 制約と RLS が同じ誤った前提から作られていれば、両方が緑でも独立ではない。

| 検出源 | 独立性 | なぜ |
| --- | --- | --- |
| 3A テスト | 同源 | ルールブックから書くので、ルールが間違っていれば期待値も間違う |
| DB 制約 | 条件つき | 別の場所で守るが、前提はルールブックと同じことが多い |
| RLS | 条件つき | 同上 |
| 層間突合 | 条件つき | ずれは見つかるが、全層が同じ思い込みなら揃って通る |
| ミューテーション | 独立 | テストの検知力そのものを測る。期待値の正しさには依存しない |
| 実経路攻撃 | 独立 | 実装の意図ではなく、外から実際に起きることを見る |
| 実測（規模・障害注入） | 独立 | 同上。件数を作って測る・依存を止めて測ると、読んで書いた前提が外れていることが出る |
| 人の判断 | 独立 | 唯一、生成元が違う |
| 実運用 | 独立 | 同上。ただし気づくのが最も遅い |

## 読み方

まず `未分類` と `対応中` を見る。次に **`誰が値を決めたか` が `AI 提案（未承認）` の行**を見る。
そこはルール・実装・テストが同じ生成元に依存していて、揃って間違える余地が残っている。

`何が見つけたか` を数えると、投資先が分かる。

- **3A テストばかり**が見つけている → 独立根拠（ミューテーション・実経路・人のレビュー）が足りない
- **独立根拠ばかり**が見つけている → 3A の書き方が甘い。ルールブックから期待値を写すだけになっていないか
- **人の判断ばかり**が見つけている → 機械の検査が届いていない領域がある

2026-09-08 時点の 18 件は
「ミューテーション 5 / 人の判断 5 / 実測（規模・障害注入）3 / 3A テスト 2 / 実運用 2 / 層間突合 1」。

当初（2026-09-07 の 11 件）は**機械が自力で見つけたのが E-032 の 1 件だけ**で、
「人の判断ばかりが見つけている → 機械の検査が届いていない領域がある」に当てはまっていた。
翌日にミューテーションと実測を回したことで、独立根拠が 9 件（5 + 3 + 1）と過半になった。
**次に足りないのは実経路攻撃**で 0 件のまま。

**「限界に書いてあることは、書いただけでは防げない」**（E-024）。
制約カバレッジは偽陰性が残ることを自分で明記していたが、その穴からちょうど 1 件すり抜けた。
限界を書くのは**気づいたときに疑える**ようにするためで、防ぐ手当てとは別物。
制約ごとに「守るテスト」を宣言させる形にすれば閉じるが、テストは制約名を書かない
（23514 を見るだけ）ので、宣言の置き場所を決める必要がある。**次に同じ形が出たら着手する**。

**同じ型が 1 日で 2 回出た**（E-022 / E-023）。どちらも
「**消せない表（append-only）に積み上がった行**に、テストが暗黙に依存していた」形で、
しきい値を越えた瞬間から毎回落ちる。手元で使うほど壊れる方向にしか進まないので、
**3 回目が出たら機械検査にする**（「監査系の表を上限なしで全件取らない」）。
いまは 2 件なので、型として書き留めるところまでにする。
同日にミューテーション計測を回して E-034〜E-038 の 5 件が増え、独立根拠の側が 6 件になった。
**うち 2 件（E-037・E-038）は「検査そのものの穴」**で、検査を足したこと自体が次の穴を見せた（aal2 の層が測れていない・変異が実装できていない）。**3 件とも「テストはあるが結果の一部を誰も見ていない」形**で、
3A テストからは原理的に見えない（テスト自身が見ていないものを、テストは指摘できない）。
`AI 提案（未承認）` は 11 件中 4 件。値をこちらで決めた箇所ほど、
ルール・実装・テストが同じ生成元に依存していて、揃って間違える余地が残っている。

## 限界

- **分類は自己申告のまま。** 機械が強制できるのは「分類を書いたか」までで、その分類が正しいかは
  判定できない。`環境` を選べば何でも通せる（同じテストで `環境` が続くならフレーキーの合図）。
- **Bash 以外で気づいた漏れは自動で拾えない。** レビューでの指摘・実運用での発覚は手で足すしかない。
  2026-09-07 の 3 件のうち 2 件がこれで、機械は 1 件も拾っていない。
- **ミューテーションは「今の値を固定した」までしか言わない。** E-034〜E-036 で足したテストは
  「その行が今の値であること」を守るだけで、その値が業務として正しいかは何も言わない。
  値の妥当性は [`design-questions.md`](./design-questions.md)（作る前に人に聞く）側の担当。
  また、この計測は**人が `npm run test:mutation` を打たないと動かない**
  （[`mutation-testing.md`](./mutation-testing.md) の「起動の引き金」）。
- **「見つけた」と「起きていた」は違う。** ここに載るのは気づいたものだけで、
  まだ誰も気づいていない漏れは 1 行も載らない。件数の少なさを健全さの証拠に読まないこと。
- **測定そのものが壊れることがある（2026-09-10 に 3 件）。** E-070（fixture の名前が
  「これは評価用だ」と教えていた）・E-071（直した直後に同じ形を自分でやっていた）・
  E-072（テストが実物のログ置き場にゴミを積んでいた）は、どれも
  **検査が緑のまま**進行していた。緑は「守れている」の証拠ではなく、
  **「その検査が見ている範囲で違反が無い」以上のことは言わない**。
  数字を読むときは「何を測ったか」を毎回確かめる——
  E-070 の 3 件は、**回答本文を残すようにした最初の 1 回**で全部出てきた
  （それまでは判定後に捨てていたので、何が起きていたか誰も見られなかった）。
- **下書きから台帳へ移す一歩は止められない。** `npm test` が止めるのは「台帳に未分類がある」状態で、
  「そもそも台帳に書かない」ことは止められない（Stop hook が聞き続けるだけ）。
