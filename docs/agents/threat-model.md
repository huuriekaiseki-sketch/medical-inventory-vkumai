# 脅威モデル（T-xxx）

「誰が・何を狙って・どこから」と、それを止める検査（約束 `P-xxx`・不変条件 `I-xxx`・test-matrix の
種別・issue #757 の番号）の対応表（issue #757 の 22）。[約束カタログ](./promise-catalog.md)が
「誰が何をできるか」、[不変条件カタログ](./invariant-catalog.md)が「データがどういう形か」を扱うのに
対し、ここはその **上位**にあり、「守る検査がまだ無い脅威」を見えるようにする。
検査の引き出しは [security-test-catalog.md](./security-test-catalog.md)、着手順は issue #757。

## 更新ルール

- 列は固定 8 列: ID / 脅威 / 誰が / どこから / 資産 / 守る場所 / 守る検査 / 状態。列の中に `|` を書かない。
- ID は `T-` + 3 桁。区分ごとに 10 刻み（認証 00x / 施設境界 01x / 権限 02x / 整合性 03x /
  秘密と PII 04x / 供給網と CI 05x / 可用性と復旧 06x / 監査と説明 07x / AI と人間系 08x）。欠番は詰めない。
- 「守る検査」列には約束 `P-xxx`・不変条件 `I-xxx`・test-matrix の種別名・`#757-N` を書く。書いた
  `P-xxx` / `I-xxx` は各カタログに実在し、逆に各カタログの全 ID はここのどこかに現れる
  （`scripts/check-threat-model.test.sh`、CI `hooks-test` が双方向に検査する）。**新しい約束や不変条件を
  足したら、どの脅威を止めるものかをここに書く**。
- 状態は 3 語のみ: 守られている（機械で回る検査がある）/ 一部（検査はあるが列挙した経路の一部が未）/
  未（守る検査が無い。`#757-N` の番号を必ず書く）。
- **更新の引き金**: 新しい入口（API Route・RPC・Storage・Webhook・外部連携・エクスポート）、新しい資産
  （決済・添付ファイル・他施設との共有）、新しい主体（開発者以外の利用者・代理店・plugin の導入先）、
  事故、外部公開の前。これらが起きたら「誰が / どこから / 資産」の表を先に見直し、脅威の行を足す。

## システムの形（信頼境界）

```
利用者のブラウザ ──(HTTPS)──▶ Vercel: Next.js（proxy.ts、API Route、画面）
      │                              │ anon key + 利用者の JWT（RLS が効く）
      │ anon key + JWT を持てば       ▼
      └────────────────────────▶ Supabase: PostgREST / RPC / Auth（RLS・SECURITY DEFINER・トリガー）
                                       ▲ service_role（RLS を通らない。サーバー側と CI・ダッシュボードのみ）
GitHub Actions（CI、ローカル Supabase）／ Supabase ダッシュボード・CLI ／ Vercel 環境変数
AI エージェント（Claude Code・Codex）: リポジトリ・ローカル DB・gh・npm に到達できる
```

実効的な境界は **DB（RLS・RPC の認可・トリガー）**。Next.js の proxy と画面は正規ルートの UX であり、
anon key と JWT はブラウザにあるので、利用者は Next.js を経由せず Supabase を直接叩ける
（[decisions/db-rls.md](./decisions/db-rls.md)）。
