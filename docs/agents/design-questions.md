# 作る前に聞く質問（design-questions）

新しいテーブル・API・外部送信を作る**前に**、人に聞いて決めておくことの一覧。

## なぜこれがあるか

2026-09-06〜07 に issue #757 の点検で見つけた実害は、**どれも「作る前に一言聞いていれば防げた」もの**だった。

| 見つかった実害 | 聞いていれば防げた質問 |
| --- | --- |
| 自由入力に上限が無く、術式名に 1 MB が保存できた | 「この文字列は何文字までですか」 |
| 施設が 12,000 件で削除できなくなっていた（外部キーに索引が無い） | 「この表は何件まで増えますか。親を消したら何が連鎖しますか」 |
| 利用者一覧が 50 人で切れていた | 「一覧は何件まで出しますか。それを超えたらどうしますか」 |
| マスタの書き込みに TOTP が要らなかった | 「これは誰が書けますか。パスワードだけの人も書けてよいですか」 |
| 読み取りが aal1 のまま全施設に届いていた | 「これは誰が読めますか」 |
| 拒否された操作が 1 件も残っていなかった | 「失敗したとき、何が記録に残りますか」 |
| 招待メールが連続で何通でも送れた | 「1 人が 1 時間に何回までできますか」 |

**点検で見つけるのは高くつく。**実装が終わってから直すと、migration をもう 1 本書き、既存行を確認し、
テストを足し、ルールブックに行を足すことになる。作る前に 5 分聞けば、最初から入っている。

## 使い方

新しいテーブル・API・外部送信を設計するとき、下の質問のうち**該当するものを人に聞く**。
分からないまま既定値を勝手に置かない（今日はそれをやって、後から全部やり直した）。

聞いた答えは、その機能の migration か route の先頭コメントに `-- design:` / `// design:` で残す。
どこで決めたかを残すのは、後から「なぜこの値なのか」を辿れるようにするため。

新しいテーブルを作る migration に `-- design:` が無ければ
`scripts/check-design-questions.test.sh`（CI `hooks-test`）が止める。

## 質問

### 1. 大きさ（1 件あたり）

- この文字列は何文字までですか（自由入力は必ず聞く）
- 数値の範囲は。負の値・0 は許しますか
- 1 件にぶら下がる子の件数に上限はありますか

守る場所は DB の CHECK（[invariant-catalog](./invariant-catalog.md) の 06x）。
画面の maxlength は利便性であって防御ではない（API を直接叩けば通る）。

### 2. 量（何件・何回）

- この表は何件まで増えますか。1 桁増えたら何が遅くなりますか
- 一覧は何件まで出しますか。超えたら何が起きますか（切る・ページを繰る・エラー）
- 1 人が 1 分・1 時間に何回までできますか

上限を決めたら quota-inventory（Q-xxx）に行を足す。

### 3. 権限（誰が）

- これは誰が読めますか。誰が書けますか
- パスワードだけを持っている人（TOTP なし）も書けてよいですか
- admin は他施設の分も見えますか

守る場所は RLS。約束は [promise-catalog](./promise-catalog.md) に ID 付きで書く。

### 4. 消えるとき

- 親（施設・利用者・商品）が消えたら、これは消えますか・残りますか
- 消えないなら、なぜ残しますか（証跡・別施設からも参照される、など）
- 消えるなら、その連鎖は件数が増えても終わりますか（外部キーの索引）

### 4b. 間違えたとき（2026-09-08 に足した）

- **利用者が間違えて登録したら、製品の中で直せますか**（取り消し・編集）
- 直せないなら、それは意図した判断ですか。**誰かが手で DB を触るしかない**状態になっていませんか
- 直せるなら、誰が直せますか。いつまで直せますか。**直した記録は残りますか**
- 消す（DELETE）のか、取り消し状態にするのか。証跡を残すなら後者
- **その取り消しは、ほかの操作が済んだ後でもできてよいですか**（2026-09-09 に足した）。
  後続の操作（返却・出荷・請求）が記録された後に前の操作を取り消せると、
  **記録どうしが矛盾する**。順番を決めるか、後続があるときは止めるかを 1 回決める

**なぜ足したか（E-056）**: 発注 3 種と返却の API は GET と POST だけで、DELETE も PUT も無い。
ところが **DB は施設の writer に DELETE を許している**（実測）。層が食い違ったまま、
**間違えた返却を製品の中では直せない**状態になっていた。
上の『消えるとき』は**親が消えたときの連鎖**しか聞いておらず、
**利用者自身の間違い**を聞いていなかった。1 つ聞いていれば、作る段階で気づいた。

### 4c. 親を消してよいか（2026-09-10 に足した）

**マスタを消すと、それを使っている施設のデータまで消えることがある。** その可否を先に聞く。

- **そのマスタは、使われていても消せてよいですか。** 消せる場合、参照している行はどうなりますか
  （一緒に消える／消せなくなる／参照だけ外れる）
- **「消せる」と決めた道が、実際に通れることを測っていますか。** 契約に「消せる」と書いてあっても、
  FK や権限で**実際には誰にも消せない**ことがある（下の実例）

**実例（2026-09-10 に見つけた）**: 契約 O-052 は「代理店商品は admin + aal2 が消せる」だが、
仕切値を一度でも変えた商品は `price_histories` からの FK に止められて**誰にも消せなかった**。
履歴は GRANT が SELECT のみなので、先に履歴を消す回避もできない。
見つかったのは、統合テストの後片付けの削除が毎回失敗していたのを機械で測ったとき
（それまでは戻り値のエラーを誰も見ていなかった）。

**まだ決まっていないこと（人に聞く）**: 施設が使っている代理店商品を admin が消せてよいか。
`hospital_prices.distributor_product_id` は `ON DELETE CASCADE` なので、
消せる場合は**全施設の仕入価格が一緒に消える**。2026-09-10 の変更ではこの可否は変えていない
（消せる前提のまま、消せない不整合だけを直した）。

### 5. 記録

- これが成功したとき、何が残りますか
- **失敗した・拒否されたとき、何が残りますか**
- 記録に患者情報や施設 ID が入りますか。入るなら誰が読めますか

### 6. 途中で止まったら

- 2 段以上ありますか。1 段目だけ成功したら何が残りますか
- 利用者がもう一度押したら、行は増えますか
- 増えないなら、何を鍵にして同じ操作だと判断しますか

### 7. 外に出るもの

- 外部サービスへ出ますか（メール・ストレージ・AI・Webhook）
- 従量課金ですか。1 人がどれだけ使えますか
- 送った内容は取り消せますか
- **回数を数えるなら、送信に失敗したとき消費は戻しますか**
  （2026-09-07 に M-021 を実測して足した質問。この製品の答えは「**送信失敗だけ戻す**」＝
  外部サービスが 5xx を返した＝出ていないことが確実なときだけ戻し、
  利用者側の誤り（422 など）は戻さない。2026-09-08）

## 4 層を揃える（作る段階でやる）

値を決めたら、**同じ条件が 4 つの層で揃っているか**を作る段階で確かめる。
2026-09-07 に見つけた実害 8 件のうち **6 件が層の間の食い違い**だった。どれも点検で見つけたが、
作るときに 1 分見比べていれば起きなかった。

| 層 | どこ | 何を持つか |
| --- | --- | --- |
| UI | `src/components/` `src/app/` | 入力欄の maxlength・必須の印。**利便性であって防御ではない** |
| API | `src/lib/validation/schemas.ts` | 入口で弾く条件。上限は `aidd.config.json` から読む |
| ロジック | `src/types/` `src/lib/*/repository.ts` | 型の必須・任意。ここと API がずれると型が守っていない |
| DB | `supabase/migrations/` の CHECK | 最後の防波堤。API を通らない経路はここだけが守る |

### 実際に起きた食い違い（2026-09-07）

| 食い違い | 何が起きたか |
| --- | --- |
| API が DB より緩い | 数量 0 を API が通し、DB の CHECK（I-010）で 23514 になった。利用者には何も伝わらない |
| API が DB より厳しい | 互換の備考が API 500 文字・DB 1,000 文字。どちらが本当か分からない |
| 型を API が見ていない | 代理店商品の入数・償還価格が型では必須なのに API が検査せず、未定義のまま DB へ |
| 設定と DB がずれている | 医師名・使用期限・仕入先が DB にあるのに「決めた値」の表に無かった |

### 機械での突合

`scripts/check-layer-consistency.test.sh`（CI `hooks-test`）が DB と API を**値まで**突き合わせる。

両側とも実物から自動で取り出す。**手で書き写す場所を作らない。**

| 側 | 取り出し方 |
| --- | --- |
| DB | `scripts/lib/scan-db-constraints.mjs` が migration を適用順に畳み込み、CHECK を列挙する |
| API | `scripts/lib/extract-api-rules.ts` が zod スキーマを**実行時に内省**して実際の値を取り出す |

対応付けは命名規約から導く（列名 `snake_case` → フィールド名 `camelCase`）。
人が書くのは `scripts/lib/layer-map.json` の 2 つだけ。

- `tables` … 表 → zod スキーマ名（規約で導けない対応）
- `columns` … 規約から外れるものだけ
  - `api: "<スキーマ名>.<フィールド名>"` … 名前が規約と違う対応
  - `serverOnly: "理由"` … 利用者が送れない列（恒久。**期限は付けない**）
  - `exception: "理由", until: "YYYY-MM-DD"` … 一時的に揃っていないことを認める。
    **期限は必須で、過ぎたら落ちる**

比べるのは種類ではなく**値**。長さ 500 対 1,000、下限 0 対 1、固定語の顔ぶれの違いを名指しする。

**恒久の分類（serverOnly）に期限を付けない理由**: 監査ログの列が将来 API から書けるように
なることはない。恒久の分類に期限を付けると、意味の無い更新作業が毎年発生する。
期限が要るのは「今は揃っていないが、いずれ揃える」ものだけ。

UI 層はまだ対象外（入れるときは対応表に `ui` のキーを足す）。

## 答えの置き場所（派生先リポジトリはここだけ書き換える）

聞いて決めた値は**文章ではなく設定**に置く。置き場所はリポジトリ直下の `aidd.config.json` の
`limits`。形（どのキーが要るか）は共通側の `scripts/lib/aidd-config.schema.json` が決め、
値はリポジトリごとに違う。

```json
"limits": {
  "decidedOn": "2026-09-07",
  "decidedBy": "決めた人の名前",
  "textLength": { "術式名などの役割名": 200 },
  "requestsPerMinute": 300,
  "invitesPerDay": 50
}
```

`textLength` のキーは**そのリポジトリの語彙**で書く。この製品は術式名・患者 ID だが、
別の製品では受注者名・本文になる。共通側はキーの名前を決めない（数と形だけを決める）。

`scripts/check-design-answers.test.sh`（CI `hooks-test`）が、キーの欠け・置き換え忘れ
（TODO・0・空）・`decidedBy` が人でない（AI・既定値）・決定日が 2 年以上前、を検知して止める。
**新しいリポジトリでは値が入るまでこの検査が落ち続ける**ので、作り始める前に人へ聞くことになる。

**2026-09-07 追記**: zod で API 入口の検証を作るとき、DB の CHECK 制約と設定を突き合わせて
**表に無い項目が 3 つ**（医師名 100・使用期限の文字列 100・仕入先 200）あることが分かった。
人が「現在の値のまま確定する」と決め、設定と表に足した。
以後は `scripts/check-text-length-consistency.test.sh` が
「設定の項目」「DB の CHECK」「API の検証」の 3 つが揃っているかを機械で突き合わせる。

未実装のものは quota-inventory（Q-xxx）の状態で追う。値が決まっていることと、入っていることは別。

**2026-09-08 追記（決めてその日のうちに実装したもの）**: 「短貸を分割して返す運用がある」ことを確認し、
同日に実装した。`loan_return_items.loan_order_item_id` で明細どうしを紐付け、部分 UNIQUE を外し、
借りた数を超える返却はトリガーが拒否する（I-063 / P-050 を書き換え）。

**残っている限界**: 紐付けの無い返却（対象の短貸発注を選ばずに記録したもの）は残数に影響しない。
「とりあえず返却だけ記録する」経路を塞がないための意図的な扱いで、その返却は未返却の数を減らさない。

**2026-09-09 追記（4b にもう 1 つ足りなかった質問）**: 「直せますか」は聞いたのに、
**「直せる操作どうしが噛み合うか」を聞いていなかった**。
取り消し（E-056）を作った翌日に実測すると、返却が記録された発注をそのまま取り消せて、
返却の行は取り消された発注を指したまま残っていた。
`### 4b` に「**その取り消しは、ほかの操作が済んだ後でもできてよいですか**」を足した。
1 つの操作だけを見て「直せるようにした」で終えると、**操作どうしの順番**が誰も決めていないまま残る。
