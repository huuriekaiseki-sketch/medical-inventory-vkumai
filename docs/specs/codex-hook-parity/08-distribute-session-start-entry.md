## 配って分かったこと（2026-09-30）

**入口は、Codex から動かすと、合計 5 秒の上限に達しました。** GitHub へ問い合わせる点検（長く止まったままの課題）が、途中で打ち切られています。入口を直接動かしたときは 12 個で 1.8〜3.5 秒でしたが、Codex からは足りませんでした。測ったのは 1 回で、毎回そうなるかは分かっていません。

このままだと、次のようになります。

- 「結果の出ていない点検があります」の知らせが、セッションのたびに入る
- 長く止まったままの課題の見張りは、結果を出さない
- 最初の発言を送ってからモデルが動き出すまでに、約 7 秒かかる（上限に達しなかった回は約 3 秒。記録の時刻からの推定）

どうするかは未決です。

| 案 | 内容 | 注意点 |
| --- | --- | --- |
| 1 | GitHub へ問い合わせる点検を、入口から外す（11 個にする） | 長く止まったままの課題の見張りは、Codex では動かなくなる。入口は 2 秒ほどで終わる見込み。hook の定義は変わらないので、信頼の操作は要らない |
| 2 | 上限を 8 秒に上げる | 最初のターンの待ち時間が、さらに伸びる。GitHub の応答が遅い日は、それでも打ち切られる |
| 3 | そのままにする | 上の 3 点が続く |

どの案でも、配るには版を上げる必要があります（0.1.6）。

### その後に分かったことと、決めたこと（同日）

**上の見立ては、半分まちがっていました。** 上限に達したのは、版を上げた直後の 1 回目だけで、2 回目からは収まっています。主な原因は通信ではなく、ファイルが新しいときの初回の起動の遅さでした。

| 測ったもの | 結果 |
| --- | --- |
| 配布物を複製した直後に入口を起動（11 個。GitHub へ問い合わせる 1 個を外した状態） | 4.8 秒 |
| 同じ場所から続けて入口を起動（同じ 11 個） | 0.8〜1.0 秒 |
| 配った 0.1.5 のまま、Codex の 2 回目のセッション（12 個） | 打ち切りなし |

最初は案 1 に決まり、実装まで進めましたが、この結果を見て取りやめました。

- 案 1 では、版を上げた直後の 1 回目は防げません（通信なしの 11 個でも 4.8 秒）
- 2 回目からは、何もしなくても打ち切られていません
- 案 1 を採ると、長く止まったままの課題の見張りが、Codex では動かなくなります

**決定: 0.1.6 は出さず、0.1.5 のままにします。** 版を上げた直後の 1 回だけ、「結果の出ていない点検があります」の知らせが入ることがあります。

上の「このままだと、次のようになります」の 3 点のうち、1 点目（セッションのたびに入る）と 2 点目（結果を出さない）は、当たっていませんでした。

# Part 1 — 仕様（★人間がレビューする部分）

## 何ができるようになるか

普段の作業場所で Codex を起動したときにも、セッションの始まりに 12 個の見張りが動くようになります。

仕様書 07 では、入口をリポジトリの `.codex/hooks.json` にだけ登録しました。実機で確かめると、普段の作業場所ではリポジトリの hook が Codex に読み込まれず、入口は動きませんでした。既存の 8 個が動いていたのは、同じものをプラグインでも配っていたからです。入口も同じようにプラグインで配ります。

# Part 2 — 実装計画（AI 用・レビュー不要）

## 根拠（2026-09-30 実測）

- 12 本の点検が頼っている部品: `lib/resolve-log-dir.sh` / `lib/run-freshness.py` / `lib/worktree-hash.sh` / `lib/aidd-doctor.mjs`（と、その import 先）。`lib/gate-prompt-hash.mjs` と `lib/rls-mutants.json` は導入先の資産で、無ければ点検が黙る（既に免除の一覧にある）
- 12 本とも、根は `${CLAUDE_PROJECT_DIR:-<スクリプトの位置>}` か git の問い合わせで決める。プラグインから動かすと、スクリプトの位置はプラグインのキャッシュになる。Claude Code のプラグインでは `CLAUDE_PROJECT_DIR` が根を教えている
- Codex 用プラグインの生成は、`codexHookScripts` の `*.sh` を `scripts/` の直下へ複製するだけで、`lib/` を運ぶ道が無い

## 実装セット

| セット | 触るファイル | 内容 |
| --- | --- | --- |
| A | `scripts/codex-session-start.sh` と テスト | 点検へ渡す根を、git の最上位（取れなければ入力の `cwd`）から決めて `CLAUDE_PROJECT_DIR` に入れる。引き継いだ値は使わない |
| B | `scripts/lib/build-plugin.mjs` / `scripts/lib/plugin-layout.json` | Codex 用プラグインへ部品を運ぶ宣言（`codexSupportFiles`）を足す。入口と 12 本を `codexHookScripts` に足す。版を 0.1.5 に |
| C | `scripts/build-plugin.test.sh` / `scripts/codex-plugin-layout.test.sh` | 配布物に入口・一覧・12 本・部品が入っていること。配布物の入口を、空の導入先を模した場所で動かして異常終了しないこと |
| D | `docs/plugin/codex-vkumai/`（CHANGELOG / KNOWN-LIMITS / COMPATIBILITY）、`docs/plugin/CHANGELOG.md`、`docs/plugin/RELEASE.md` | 0.1.5 の節。人の画面に出ないこと・信頼の操作が 1 回要ることを既知の制約に書く |
| 統合 | `scripts/lib/codex-hook-gap.json` の説明、`docs/agents/file-index.md`、仕様書 07・索引 | 「配っていない」の記述を直す |

## テスト観点

- 引き継いだ `CLAUDE_PROJECT_DIR` が別の場所を指していても、点検に渡るのは git の最上位
- git の外で起動したときは、入力の `cwd` を渡す
- 配布物の `hooks/hooks.json` に、入口が `"${PLUGIN_ROOT}"/scripts/codex-session-start.sh` の形で 1 件ある。既存の登録の並びは変わらない
- 配布物だけを置いた場所から入口を動かし、計測の記録も運用文書も無い作業場所を見せたとき、exit 0 で、起動できない点検が 0 本
- 壊して落ちる: 部品の宣言を 1 つ消すと、生成が「同梱されていない」で落ちる

## 配布と実機確認

`docs/plugin/RELEASE.md` の手順どおり。版上げの PR → marketplace へ push → タグ 4 本 → 個人環境の更新 → **人が `/hooks` で入口を信頼** → 普段の作業場所で Codex を起動 → セッションの記録の `developer` の発言で発火を確認。
