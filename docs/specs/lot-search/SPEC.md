## Part 1 — 仕様（人間レビュー用）

### 1. 何ができるようになるか

リコールの連絡が来たとき、ロット番号を入れると、その施設の

- 症例発注の明細（`case_order_items.lot`）＝ **症例で使った物**
- 短貸返却の明細（`loan_return_items.lot`）＝ **返した物**

のうち、そのロットが出てくる行が一覧で出る。各行から元の発注・返却へ辿れる。
読み取り専用。既存の発注作成・更新・返却登録の挙動は変えない。

**対象外であることを画面に書く**: 短貸発注の明細（`loan_order_items`）には `lot` 列が無い（`jan` のみ）。
「借りた時点のロット」は引けない。在庫のテーブルも無いので「いま棚にある物」も引けない。

### 3. 操作の流れ

1. 施設の画面からロット検索（`/facilities/[id]/lot-search`）を開く
2. ロット番号（1〜100 字）を入れて検索する。Enter でも実行できる
3. 検索中は検索ボタンを押せなくし、待っていることが分かる表示を出す
4. 結果を「症例発注」「短貸返却」の種別つきで一覧に出す（種別は色だけでなく文字でも区別）
   - 出すもの: ロット・JAN・数量・種別・日付（症例日時／返却の日付）・元の発注／返却へのリンク
   - 0 件のとき: 「該当するロットは見つかりませんでした」（検索前の初期状態と見分けがつく）
   - 上限に当たったとき: 「該当が多いため一部のみ表示しています。ロット番号を長くして絞り込んでください」
5. 入力が空・101 字以上のとき: 入力欄のそばに「1〜100 字で入力してください」
6. 通信・サーバーの失敗: 既存の画面と同じ形のエラー表示（新しいエラーの体系は作らない）

### 4. 受け入れ条件

- [ ] ロット番号（1〜100 字）で、その施設の `case_order_items` と `loan_return_items` から一致する明細が出る
- [ ] **他施設の明細は出ない。** テストを介さない直接攻撃（他施設の施設 ID・他施設ユーザーのセッション）でも出ないことを実測する
- [ ] **MFA を通していないセッション（aal1）で「0 件」を返さない。** 明細の SELECT ポリシーは
      `has_aal2() AND (...)`（`20260907000001_require_aal2_for_facility_reads.sql`）なので、aal1 だと RLS が
      全行を隠し、エラーではなく**空の結果**になる。ロット検索で空は「該当なし」と読まれる＝リコールの取りこぼし。
      画面は proxy の aal2 ガードで届かないはずだが、API を直接呼ばれた場合も含め、aal1 は拒否（または MFA 要求）に
      なることを実測する。既存の一覧 API が同じ状況でどう振る舞うかを先に確かめ、揃える
- [ ] `lot` が NULL の明細は検索対象にならない（`NULL LIKE ...` は UNKNOWN。黙って外れることをテストで固定する）
- [ ] 検索語の `%`・`_` はワイルドカードとして働かない（`%` 1 文字で全件が出ない）
- [ ] 結果の各行・エラー応答・サーバーログに、患者 ID・イニシャル・性別・医師名・術式名が含まれない（決定 6 が (a) の場合）
- [ ] 上限を超えるとき `truncated: true` が返り、画面に絞り込みの案内が出る
- [ ] 0 件・検索中・入力エラー・通信エラーのそれぞれの表示がある
- [ ] 閲覧のみのロールでも検索できる（決定 8 が (a) の場合）。未認証・非メンバーは拒否され、拒否が `access_denials` に残る
- [ ] 新しい route が `e2e/api-attack-matrix.ts` に載っている（載せないと P-017 の ratchet が CI で落ちる）
- [ ] 「短貸発注の明細は対象外」が画面に書いてある
- [ ] 既存の発注作成・更新・返却登録のテストが全部通る（挙動を変えていない）
- [ ] キーボードだけで検索から結果のリンクまで操作できる

### 5. 今回やらないこと（別 issue にする）

- 索引の追加。**中間一致では btree 索引は `lot` に効かない**（効かせるなら `pg_trgm` + GIN で、拡張の追加は別の判断）。
  今回は migration を作らず、実データ規模で応答時間を 1 回測って記録する。遅ければ別 issue
- 表記ゆれの本格的な吸収（決定 3 の (c)）
- 読み取りの監査記録（決定 7 の (b)）
- 全施設の横断検索（決定 1 の (b)）
- 使用期限（`ubd`）のアラート、ロット別の在庫（在庫のテーブルが無い。issue #803 の「対象外」参照）

## Part 2 — 実装計画（AI 用）

### 守りは 3 層。どれも省かない

1. **RLS**: `case_order_items` / `loan_return_items` の SELECT ポリシーは
   `has_aal2() AND EXISTS(親の facility_id について is_facility_member(...) OR is_admin())`
   （最新の定義は `20260907000001_require_aal2_for_facility_reads.sql`。最初の版ではなくこれを見ること）。
   **admin は全施設ぶん通る**ので、RLS だけでは admin の検索が全施設になる
2. **repository の明示条件**: **明細の表に `facility_id` 列は無い。** 親を `!inner` で結合して
   `case_orders.facility_id = <施設ID>` を条件に入れる。RLS だけに頼らない（admin は RLS を広く通るため、
   これが無いと admin の検索が全施設になる）
3. **患者情報を型と SELECT 列の両方で持たない**: `LotSearchResultItem` に患者のフィールドを置かない（コンパイル時）。
   repository は親から `id`・`facility_id`・日付だけを選ぶ（実行時）。`log-safe.ts` は最後の網

## 承認後の訂正（2026-09-19。ここより上は承認時点のまま。承認時のハッシュは `2e09e372…f59969`）

実装フロー（`wf_df7edb9b-78c`）が Review で 3 回差し戻しても fail が残り、人に引き渡された。残った 2 件を調べた結果:

1. **セット D の「`scripts/lib/layer-map.json` に経路を足す」は仕様書の誤り。取り消す。**
   `layer-map.json` は「DB の CHECK 制約」と「**書き込み用**の zod スキーマ」を突き合わせる表（同ファイルの `_comment`）。
   ロット検索は読み取り専用で、表も列も書き込みスキーマも増やさないので、**足すものが無い**。
   deep のドラフトにあった記述を、この表が何かを確かめずに引き継いだ。
   「重複・抜け漏れ」のレビュアーは「対象外」と正しく判断し、「仕様カバレッジ」のレビュアーは仕様書に忠実に fail を出していた
2. **受け入れ条件「aal1 で『0 件』を返さない」は、実装が条件を逆向きに書き換えていた。**
   統合テストの describe が「受け入れ条件: aal1 のセッションでは 0 件になる」になっていた（条件を実測に合わせた）。
   条件の本文（「aal1 は拒否（または MFA 要求）になることを実測する。既存の一覧 API に揃える」）は変えず、満たし方を次のとおりにした:
   - 既存の施設スコープの読み取り API は route で aal を見ない。aal1 を届かせないのは **proxy の MFA ガード**
     （`src/proxy.ts`。matcher が `/api/*` を含む）。ロット検索もこれに揃える（route に新しい分岐は足さない）
   - `src/__tests__/proxy.test.ts`: aal1 でロット検索の API を直接呼ぶと 307 で `/mfa-challenge` へ送られる／
     **matcher が API のパスを含む**（このファイルのテストは全部 `proxy()` を直接呼ぶので、matcher を見るテストが 1 本も無かった。
     matcher から `api` を外して落ちることを実測済み）
   - 画面: リダイレクト先の HTML（200 だが JSON でない）を「0 件」と表示しない、をテストで固定
   - 統合テストの aal1 の 1 本は「受け入れ条件」ではなく「**proxy を通らない経路ができたら黙って 0 件を返す、の DB 層での証拠**」と書き直した
