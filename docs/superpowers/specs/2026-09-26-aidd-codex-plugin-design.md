# Codex 用 AIDD プラグイン設計仕様（レビュー案）

作成日: 2026-09-26

状態: 設計レビュー待ち。実装・インストール・実走検証は未実施。

想定利用者: 個人の Codex に導入し、複数の Git リポジトリで使う開発者。

## 1. 目的と前提

医療在庫管理リポジトリで育てた AIDD の判断と検査を、Codex でも繰り返し使える形にする。Claude Code と Codex は同じ製品リポジトリで作業できるが、同じ物理 worktree を同時に使わず、各ツールの hook・権限・実行中の状態は分離する。共通にするのは、守る約束、機械判定のロジック、テスト fixture、証拠の形式である。

成功は「プラグインが表示される」だけでは判定しない。導入先でリスク分類、仕様承認後の改変検知、品質ゲート、検査器の空振り検知が実際に働き、サイクルごとの有効性と費用を記録できたときに判定する。

既存の参照元:

- `docs/agents/harness-map.md`: 守る対象・前提・実測・反証の分離。
- `docs/agents/escaped-defects.md`: 過去の見逃しから作った回帰検査。
- `docs/agents/portability-inventory.md` と `scripts/lib/plugin-layout.json`: 共通部と固有部の区分。
- `docs/agents/parallel-agent-work.md`: Claude Code / Codex の共存規則。
- `docs/agents/run-manifest.md`: 仕様ハッシュと承認の突合。
- `docs/agents/harness-score.md`: 止めた・見逃した・邪魔したという実績の記録。
- `docs/specs/plugin-v1/SPEC.md`: Claude Code 用プラグインの設計と検証経験。

2026-09-26 に確認した現行の [OpenAI プラグイン構成](https://developers.openai.com/plugins/build/plugins)では、Codex 向けにスキルと hook を同梱でき、個人のローカル marketplace で配布できる。旧仕様書の「Codex にはプラグイン機構が無い」は当時の制約として扱い、本設計の前提にはしない。ただし plugin 同梱 hook はインストールだけでは信頼されず、利用者が確認・信頼する必要がある。

## 2. 設計方針

推奨案は **スキル + 決定的な判定スクリプト + 必要最小限の Codex 用 hook** である。

| 案 | 利点 | 限界 | 判断 |
| --- | --- | --- | --- |
| スキルだけ | 配布と更新が簡単 | フェーズ順・ハッシュ・記録を自然言語の自己申告に依存 | 採用しない |
| スキル + 判定スクリプト + hook | 共通ロジックを検査でき、Codex 固有の入口を分離できる | パッケージと実機検証が必要 | 採用 |
| MCP サーバーでフローを制御 | 明示的なツール契約を作れる | サーバーの運用・認証・可用性が増える | 必要性が実測されるまで保留 |

判定ロジックを Claude Workflow のプロンプトから複製しない。既存の純粋関数・スクリプトを候補に、依存関係と配布先での動作を調べてから共通化する。Claude 固有の transcript、Workflow DSL、hook の出力契約は Codex プラグインへ持ち込まない。

### 2.1 層と責任

| 層 | 正本・役割 |
| --- | --- |
| 共通判定 | リスク分類、Run Manifest の検査、品質ゲート、証拠スキーマ、検査器の反証テスト。中心リポジトリの追跡可能なソースを正本とする |
| `aidd-codex` | Codex 向けスキル、CLI 入口、hook アダプター、ローカル実行記録。個人 marketplace から導入する |
| Claude Code 用プラグイン | Claude 側の Workflow・agent・hook アダプター。既存経路を継続する |
| 導入先リポジトリ | `aidd.config.json` 相当の固有設定、製品テスト、DB・認証・デプロイ環境、必要な `AGENTS.md` / `CLAUDE.md` |

初版は中心リポジトリから Codex 用配布物を決定的に生成する方針とする。既存の Claude 用生成と同じく、生成物を手で直さない。生成対象外にする資産には理由を記録し、正本と生成物の差分を CI で検出する。プラグイン自体を正本へ反転するかは、複数リポジトリでの実績を得てから判断する。

### 2.2 想定パッケージ

```text
aidd-codex/
  plugin.json                  # portable manifest。必要なら Codex 用 overlay を追加
  skills/aidd-run/SKILL.md     # フェーズと人間ゲートの入口
  skills/aidd-review/SKILL.md  # 最終レビューの入口
  scripts/                    # 判定・記録・doctor。実装時に依存を精査
  hooks/hooks.json            # Codex の出力契約に合うものだけ
  schema/                     # 設定、Run Manifest、実行結果のスキーマ
  tests/                      # 配布物単体・空リポジトリ・故障注入用 fixture
  COMPATIBILITY.md
  KNOWN-LIMITS.md
  CHANGELOG.md
```

MCP、外部 DB、クラウド認証、デプロイは初版の必須要素にしない。スクリプトは導入先のローカル Git 作業ツリーを対象に実行する。製品固有の Supabase・Next.js 検査は、プラグイン共通部ではなく導入先設定またはアダプターに置く。

## 3. 実行フロー

フェーズは既存の「調査 → 仕様 → 実装 → 統合 → 検証」を保つ。軽量・深掘りのどちらへ進むかは、変更パスを優先する機械判定で決める。説明と変更ファイルが食い違う場合、判定材料が不足する場合、設定が壊れている場合は軽量ルートへ黙って落とさず `confirm` または `blocked` とする。

| 段階 | 入力 | 成果物・通過条件 |
| --- | --- | --- |
| 開始 | タスク説明、基点コミット、候補変更パス、導入先設定 | 実行 ID、リスク分類、適用した設定版を記録 |
| 調査 | リスク分類と対象パス | 調査範囲・未読範囲・指摘を構造化。担当 role の実行方法は Codex 側で検証して確定 |
| 仕様 | 調査結果 | 人間向け仕様と技術契約を保存。仕様レビューで停止 |
| 承認 | 人間が確認した仕様 | 仕様 SHA-256、承認者・時刻、基点コミットを Run Manifest に記録 |
| 実装 | 承認済み Manifest | 契約とファイル所有者を先に決める。仕様ハッシュの不一致・未承認なら開始を拒否 |
| 統合 | 実装結果、変更ファイル | 導入先が宣言した必要テストを実行。未実行・確認不能・失敗を区別する |
| 検証 | 差分、仕様、テスト証拠 | 独立レビューと結果の突合。人間が起動する最終レビューで停止 |

フェーズの状態遷移と `pass / fail / blocked / unknown` の判定は CLI が行う。スキル本文は手順と説明を担うが、エージェントの「完了した」という文章だけで状態を進めない。中断後の再開では、仕様ハッシュ、基点コミット、既存の結果、現在の Git 状態を再確認する。

Codex の role 配布は **未確定の設計ゲート**である。既存の `.codex/agents/*.toml` をプラグインが自動認識するとは仮定しない。公式仕様で確認できるパッケージ要素はスキル・MCP・hook であるため、実装前に (a) role 指示をスキルの参照ファイルから渡す、(b) 導入先の `.codex/agents` を生成する、の両案を実機で比較する。並列実行を保証できない環境では順次実行と明示し、実行数を偽らない。

## 4. 両ツールの共存と hook

同じリポジトリで Claude Code と Codex を使う。ただし同じ物理 worktree の同時編集は禁止し、`claude/*` と `codex/*` の作業ブランチ・PRを分ける。共有できる安全判定は `scripts/` のツール非依存部分を呼び、hook の登録・stdin/stdout 契約・状態保存先は分ける。

| 目的 | 共有するもの | 分けるもの |
| --- | --- | --- |
| 直接 DDL 等の危険操作を防ぐ | コマンドと対象の判定 | Claude と Codex の PreToolUse アダプター |
| 品質チェックの実行漏れを知らせる | 必要チェックの導出規則 | 発火イベントと実行記録の読み取り方 |
| フェーズを再開する | Manifest の意味・検証関数 | 実行中の状態ファイルとセッション識別子 |
| 検査器の空振りを防ぐ | fixture と期待する失敗 | 両ランタイムでの hook 発火実走 |

Codex プラグインの hook は利用者が信頼を確認するまで非稼働と扱う。hook の有無、信頼状態、必要な実行系、実発火の結果を doctor が別々に報告する。未信頼・未発火を「保護済み」と表示しない。既存の Codex project hook と plugin hook が同じ処理を二重に実行しないよう、登録場所を選ぶ規則と重複検査を設ける。

## 5. 記録と効果測定

各実行の機械ログは Codex 専用の非追跡領域に置き、Claude 側の `logs/` と混ぜない。共有するのはイベントのスキーマと、根拠を確認した後の集計結果である。患者・施設などの実データ、資格情報、プロンプト全文は記録しない。

最低限、`runId`、ツール名と版、リポジトリ・コミット、リスク判定、対象になったゲート、実際に走ったゲート、結果（通過・停止・失敗・確認不能・対象なし）、証拠への参照、所要時間を残す。トークン・費用は取得できた場合だけ記録し、欠損を 0 とみなさない。

`docs/agents/harness-score.md` の「止めた・見逃した・邪魔した」は結果の評価として維持する。一方、分母として「発動機会」を追加し、実行しなかったゲートも数える。後日判明した欠陥を元の run / issue に結び、見逃しへ再分類できるようにする。初期の記録形式と既存 `harness-score.jsonl` の互換性は、移行方法を決めてから変更する。

## 6. 検査計画と受け入れ条件

これは**将来の実装を受け入れるための計画**であり、本仕様作成時には実行しない。

| 検査層 | 確認すること |
| --- | --- |
| 判定ロジック単体 | リスク分類、仕様ハッシュ、状態遷移、重大度判定、重複実行の冪等性 |
| 構造・配布物 | 正本と配布物の一致、同梱漏れ・幽霊ファイル、禁止された固有語、依存の閉包、2回生成して差分ゼロ |
| 空振り・故障注入 | 0件走査、壊れた fixture、欠損した実行系、hook の no-op 化、仕様改変で検査が赤になること |
| クリーン環境 | 別の小さな Git リポジトリに個人 marketplace から導入し、設定・スキル・hook の状態を確認 |
| 実機 | Codex で hook を信頼した前後の発火、危険操作の拒否、停止ゲート、再開、role の権限と実行方法 |
| 共存 | Claude と Codex の状態・ログが混ざらず、同じ判定 fixture に対して同じ意味の結果になること |
| 実案件 | 軽量・高リスクの実サイクルで、対象ゲートと実行結果が欠けずに記録されること |

「Codex でも利用可能」と報告する条件は、パッケージ検証だけでなくクリーン導入先での実走を含む。hook が未信頼、必須ゲートが未実行、結果が確認不能なら、その範囲は未検証と表示する。プラグインを変更する PR は、対象コミットの必須 GitHub Actions がすべて `success` になってから統合する。

## 7. 作業区分と実装順

| 区分 | 項目 |
| --- | --- |
| 今回実施 | リポジトリと現行公式仕様を調べ、本レビュー用仕様書を作る |
| ユーザーまたは外部環境の準備待ち | 仕様への Claude Code レビュー、個人 marketplace へのインストール時の hook 信頼確認。後者は実装段階で行う |
| 後続の別タスク | role 配布方式の検証、共通判定の抽出、配布物生成、テスト fixture、実機訓練、複数リポジトリ導入、サイクル測定 |

実装時は、(1) 正本と配布範囲の決定、(2) 判定スクリプトとテスト、(3) スキルと Manifest、(4) Codex hook と doctor、(5) クリーン環境・共存実走、(6) 実案件の測定、の順に小さな変更として進める。各段階で対象・検査結果・残る未検証範囲を示す。GitHub、Supabase、本番 DB、デプロイへの接続は、このプラグインの初期構築には必要ない。

## 8. Claude Code レビューで確認したい論点

1. 共通判定の正本を中心リポジトリに残し、Codex 配布物を生成する方針は、既存 `aidd-core` の正本・配布区分と矛盾しないか。
2. Codex の role をスキル参照と導入先生成のどちらで表すと、権限と変更追跡を検証しやすいか。プラグインだけで agent 定義が有効になるという未検証の前提を置いていないか。
3. plugin hook と既存 project hook の二重発火、hook の未信頼、実行系欠損を確実に発見できるか。
4. 仕様承認後の改変、状態の再開、`blocked` の戻り先に抜けがないか。
5. 実行ログの「対象なし」「未実行」「確認不能」「失敗」を混同せず、分母を含む効果測定になっているか。
6. vkumai 固有の RLS・医療データ検査が共通プラグインへ漏れていないか。

## 9. 未確定事項と限界

- Codex プラグインが `.codex/agents/*.toml` を配布・認識する経路は未確認。設計ゲートとして実測してから決める。
- plugin 同梱 hook の発火・信頼状態をプログラムからどこまで検査できるかは未確認。実機で不足があれば、信頼確認を必須の手順として明示する。
- 深掘りルートの並列数、モデル指定、費用上限は Codex の実測前に Claude 版の値をコピーしない。
- 費用対効果の統計的な判定閾値は、記録が集まってから定める。初期値「1回止めたら維持」は長期判断の根拠にしない。
- 本仕様は設計提案であり、Codex の実利用可能性や Claude 版との同等性を実証したものではない。
