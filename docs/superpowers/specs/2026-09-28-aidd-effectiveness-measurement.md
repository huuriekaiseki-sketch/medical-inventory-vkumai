# AIDD ハーネス効果測定仕様（レビュー案）

作成日: 2026-09-28

対象: vkumai の実案件パイロット。計測の仕様のみで、実装・運用開始は含めない。

## 1. 目的と現状

部品を「残す・直す・外す」と判断する前に、**守る機会が何回あり、実際に動き、何を見つけ、いくら掛かったか**を同じ単位で記録する。まず記録方法を10件で試し、最大20件まで広げる。多数回の継続測定や他リポジトリへの導入は、その記録方法が回ると確認してから判断する。

現行の [`harness-score`](../../agents/harness-score.md) は `stopped` / `missed` / `obstructed` が起きたときだけ行を足す。2026-09-28 時点で28行・9件の `issue` があるが、何も起きなかった検査機会は記録しない。したがって、この28行から発火率・見逃し率・誤警告率は算出できない。現行の `keep` / `drop` は観測済みの出来事の仕分けであり、1件だけの `drop` を即時削除の根拠にしない。`eval-runs.jsonl` は fixture の実行記録であり、実案件の分母に混ぜない。

## 2. パイロットの単位と対象

- **1サイクル = 着手を決めた製品タスク1件。** 着手時に ID を振り、PR が複数でも1件と数える。PR を作らず中断・差し戻しになったタスクも残す。ハーネス自体の改修タスクは対象外とし、別に件数を報告する。
- vkumai で開始日以降の**連続した**製品タスクを10件採る。記録負担と欠損を見直した後、同じ規則で最大20件まで延長する。成功例だけを選ばない。過去の28行は事例として使い、新しい分母には入れない。
- 最初に見る部品は `Manifest Check`（core）、`Coverage Check`（core）、`4 観点レビュー`（core）、`深掘り Phase 1（aidd-1-1-deep-task）`（adapter）の4つ。各サイクルで4部品すべてに「対象／対象外／不明」を記録する。対象外には理由を付ける。
- Claude Code / Codex、repo 内の定義 / plugin 配布、軽量 / 深掘りルート、起点コミットを区別して記録する。両ツールを使ったサイクルは `tool = mixed` とし、単独利用の集計に混ぜない。異なる条件を合算して「Codex でも同じ効果」とは言わない。Codex プラグイン4 hook の実案件評価は、導入先を決める別パイロットで行う。

## 3. 記録の契約

導入時に `docs/agents/harness-opportunities.jsonl` を新設し、**1行 = 1サイクル × 1部品**とする。既存の `harness-score.jsonl` は出来事の台帳として残し、語彙や過去行を書き換えない。新台帳の各行には次を持たせる。

| 項目 | 記録する値 |
| --- | --- |
| 識別と条件 | `cycleId`（GitHub issue 番号、無ければ固定のローカル ID）、`repo`、`tool`、`distribution`（repo / plugin / unknown）、`baseCommit`、`route`、`component`、`layer` |
| 分母 | `eligible` = yes / no / unknown。no は `reason` 必須。unknown は分母から黙って除かない |
| 実行 | `run` = yes / no / unknown、`runCount`。no の場合は0、ログ等を読めない場合は unknown と null にし、0 回と書かない |
| 確認 | `review` = complete / pending / unknown。止めた・見逃した・邪魔した出来事は既存の `harness-score` に別行で残す |
| 費用と根拠 | 部品の実行・待ち・手戻り `overheadMinutes` と記録作業の `recordingMinutes`（未取得は null）、`ref`（PR・CI・セッション記録等の実在パスまたは URL） |

同じ `repo`・`cycleId`・`component`・`layer` の重複行は認めない。`harness-score` に出来事を記す場合、その `issue` は同じ `cycleId` とし、部品名と層も一致させる。集計はこのキーで両台帳を突き合わせる。対象 yes で run no は「未実行」であり、その部品が守るはずの欠陥を独立に確認するまで `missed` とは数えない。後から漏れが見つかったら、機会行の根拠・確認状態と出来事行を一緒に更新する。

記録担当は着手時に部品の契約から4行の対象判定と条件を置き、結果を見てから対象判定を都合よく変えない。タスクの終了・中断時に実行と費用を埋める。AI はログから下書きを作れるが、`stopped` / `obstructed` / `missed` の最終判定は、当該検査の出力だけを根拠にせず、人が PR の差分・CI・[`escaped-defects`](../../agents/escaped-defects.md) 等と突き合わせる。後日見つかる漏れは追記し、`review = pending` の機会や出来事行の無い機会を「見逃し0件」とは呼ばない。

## 4. 集計と判断

10件目と20件目に、部品・層・ツール・ルートごとに次を**分子／分母／不明件数**で並べる。少数例では率だけを出さず、件数と個別の根拠を示す。

1. **実行の確かさ:** 対象 yes の機会のうち、run yes / no / unknown。対象判定 unknown も別掲する。
2. **検知と負担:** 両台帳を突き合わせ、人が確認した有効な停止、後から独立に見つかった漏れ、誤警告・空振りの件数。`overheadMinutes` の合計・中央値と未取得件数。出来事行が無いことは欠陥不存在の証明ではない。
3. **測定自体の負担:** `recordingMinutes` と、4行を埋められなかったサイクル数。記録負担が大きければ項目を削る判断を先に行い、自動収集機構を直ちに増やさない。

10件時点の判定は「この測り方を続けられるか」。20件時点でも部品の自動削除はしない。`harness-score` の `drop` 候補には、対象機会・実行証拠・誤警告の再現・見逃しの独立した根拠を添えて人が判断する。条件が違う回を混ぜた改善率や、測れなかった費用を0とする合計は出さない。

## 5. 受け入れ条件と後続

仕様から実装へ進む際は、(a) 4部品について各サイクルに1行ずつ作れること、(b) 対象外と不明を区別し不明を集計から落とさないこと、(c) 既存 `harness-score` の28行と検査を壊さないこと、(d) 架空の対象・未実行・誤警告・後日発見した漏れを入れた対照テストで集計が期待どおり変わることを確認する。実案件の値は人が根拠を確認し、テストの緑だけを「効果あり」とは読まない。

この仕様は保存形式と判定規則を定める。記録 CLI、Codex の `PLUGIN_DATA` 連携、doctor の実発火表示、5フェーズ制御、複数リポジトリ集約、50〜100サイクルへの拡張は別の判断とする。既存の [Codex プラグイン仕様 §6](2026-09-26-aidd-codex-plugin-design.md) の後続項目を、このパイロットだけで実装済みとは扱わない。
