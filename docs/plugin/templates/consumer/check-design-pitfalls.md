# 検査の設計で間違えやすい型（C-xxx）

**検査そのものを設計するときの間違え方**を、値ではなく型で並べる。
`docs/agents/check-design-pitfalls.md` へ置き、`scripts/lib/catalog-registry.json` に登録する
（登録の雛形はこのひな形と一緒に配っている `catalog-registry.json` を参照）。

**この 12 の型は、どのリポジトリでも同じ形で出る。** 変わるのは
「どの入力検査で踏んだか」「どの認可の判定で踏んだか」といった**実例**と、
それを止める**検査のパス**だけ。だから型はプラグインが配り、実例と検査は導入先が書く。

- 状態が `検知なし` の行は、破られても機械では気づけない。**導入したばかりの時点では全部そうなる**
- 自分のリポジトリで実際に踏んだら、実例に**日付つきで 1 行**足す。
  同じ型が繰り返していることが見えるほうが、1 件ずつ直すより効く
- 止める検査を作ったら、状態を `検知あり` にして守るテストのパスを書く

## 更新ルール

- 列は固定 8 列: ID / 間違え方 / どう現れるか / なぜ気づけないか / 設計での無くし方 / 実例 / 守るテスト / 状態。列の中に `|` を書かない。
- ID は `C-` + 3 桁。区分ごとに 10 刻み（宣言と実態のずれ 01x / 判定の弱さ 02x / 範囲と単位の取り違え 03x / 確かめ方そのものの誤り 04x）。欠番は詰めない。
- 状態は 2 語のみ: 検知あり / 検知なし。
- 状態が 検知あり の行は、守るテスト列にパスを書く（`未` は不可）。
- **実例は必ず日付を書く。**「一般にありがち」で行を足さない。実際に起きたものだけを載せる。
- **更新の引き金**: すり抜けが 1 件出たときに、既存の型か新しい型かを必ず判断する。

## 限界

- **型は思いついた範囲しか載らない。** 実際に起きて実測したものだけを載せる方針なので、
  まだ踏んでいない型はここに無い。ここに無いから安全、ではない
- **型に当てはめる作業は人がやる。** すり抜けが出たときの判断は人で、その判断が漏れても機械は気づかない
- **守るテスト列は、その型の実例 1 つを止める検査**であって、型そのものを全部止めるわけではない
- **導入したばかりの時点では、すべての型に検知が無い**:
  C-010 / C-011 / C-012 / C-020 / C-021 / C-022 / C-023 / C-024 / C-030 / C-031 / C-032 / C-040 / C-041。
  自分のリポジトリで止める検査を作るたびに、その行を 検知あり に変えていく

## 読み方

- 新しい検査・仕組みを作る前に、まず **02x（判定の弱さ）** を読む。
  C-021（不在で判定するなら出る側の対を置く）と C-022（壊して落ちることを見る）は、
  この 2 つを守るだけで「緑だが効いていない」の大半が消える
- **C-023 は C-022 の先にある。** 壊して落ちることを確かめたのに落ちなかったら、
  「守れている」ではなく「手前の別の防御が止めていて、狙った防御を測れていない」を先に疑う
- **C-030 と C-041 は同じ事故の表と裏**。片方だけ直しても再発する
- いちばん危ないのは **C-012**。上に挙げた実例のうち、唯一そのまま実害になった型
