### 判定本体が欠けたとき（セッション `01a0ec27-f314-7e13-82fd-ddcb9762c5eb`、仕様書 04）

導入済み `aidd-codex` 0.1.4 のキャッシュから、判定本体 `check-skip-marker-write.sh` を一時的に退避して測った（ラッパー `codex-skip-marker-deny.sh` と `hooks.json` はそのまま）。

| 操作 | 観測 |
| --- | --- |
| シェルで `echo hello` | `Command blocked by PreToolUse hook: codex-skip-marker-deny.sh: 判定本体 check-skip-marker-write.sh が見つかりません（…/aidd-codex/0.1.4/scripts/check-skip-marker-write.sh）。 守りが効かないので止めました。プラグイン（または scripts/）を入れ直してください。` |
| `apply_patch` で `probe.txt` を新規作成 | 同じ理由で `Command blocked by PreToolUse hook`。ファイルは作られていない |

**Codex は、hook の exit 2 を「止める」と扱い、stderr に書いた文を理由として出す。** 守りと無関係な操作（`echo hello`）も含めて全部止まる。全角の括弧の直後に変数の値（パス）が正しく展開されていることも、この出力で確認できる。測定後に判定本体を戻し、sha256 が配布物と一致することを確認した（`2a4026d2…5803e179`）。

### 記録の置き場に書けないとき（仕様書 05）: 非対話モードでは確かめられない

検証用 clone の `.codex/.ai-check-suggest-state` を通常ファイルにして（`mkdir -p` が失敗する）、未追跡の `src/probe.ts` を置き、`npm run typecheck` を 1 回実行させた。比較の基準として、まず導入済みの 2 本を**直す前の版**（main `9d8bc552` の `codex-ai-check-track.sh` / `codex-ai-check-suggest.sh`。スクリプト単体では rc=1 になる）に一時的に入れ替えて測った（セッション `01a0ec39-828c-7ab1-b46c-aaae01fb4193`）。

- `codex exec --json` の出力に、PostToolUse・Stop のどちらの hook の失敗も現れなかった
- セッションの保存記録（rollout）にも、hook の失敗を示す記述は無かった（`exited with code` は、実行したコマンド自身の終了コード 254 の 1 件だけ）

**直す前の版でも失敗が見えないので、この経路では「直した後は失敗しない」ことを確かめられない。** 直した後の版での測定は、比べる意味が無いので行っていない。2026-09-28 に「Stop hook (failed)」が見えたのは対話 CLI の画面で、確かめるには対話 CLI を人が操作する必要がある。測定後に 2 本を配布した版へ戻し、sha256 が配布物と一致することを確認した。

### 測定の途中で分かったこと

検証用 clone に、空のフォルダ `.codex/.ai-check-suggest-state/` が残っていた。今日の最初の測定（0.1.3 の判定本体を一時的に差し替えた測定）のときに、0.1.3 の `codex-ai-check-suggest.sh` が `mkdir -p` で作ったもの。**空のフォルダは `git status` に出ない**ので、それまでの「クリーン」の確認では見えていなかった。仕様書 05 が直した「確認するだけの hook が導入先にフォルダを作る」の実例にあたる。0.1.4 の Stop 側はフォルダを作らない（スクリプト単体のテストで確認）。取り除いた。
