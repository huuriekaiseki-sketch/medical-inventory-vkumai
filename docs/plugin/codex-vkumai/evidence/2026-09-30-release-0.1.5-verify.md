# 0.1.5 の配布と、配布した版での実機確認

実施日: 2026-09-30。中心リポジトリ `61fa0ac2`（PR #870）、marketplace `huuriekaiseki-sketch/aidd-plugins` の `6311105`。Codex CLI 0.147.0。仕様書は [`docs/specs/codex-hook-parity/08-distribute-session-start-entry.md`](../../../specs/codex-hook-parity/08-distribute-session-start-entry.md)。

対話 CLI の操作（起動・`/hooks` の確認・信頼）は、人が行った。こちら（Claude Code 側）が行ったのは、配布・個人環境の更新と、設定ファイル・セッションの記録の読み取り。`--dangerously-bypass-hook-trust` は使っていない。

0.1.5 は、初めて **hook が増える**版（0.1.4 までは hook の定義が変わらなかった）。

## 結論

| 確かめたかったこと | 結果 |
| --- | --- |
| 普段の作業場所で、入口が Codex から発火するか | **発火する。** 3 件の知らせが、追加コンテキストとして会話に入った |
| hook を足す版で、既存の hook の信頼は保たれるか | **保たれる。** 更新の前後で、信頼の記録は 1 行も変わらなかった |
| 知らせが、人の画面に出るか | **出ない**（仕様書 07 の実機確認と同じ） |
| 合計 5 秒の上限に収まるか | **更新の直後の 1 回目は収まらなかった**（点検 1 本が打ち切られた）。**2 回目は収まった**（下の「追記」） |

## 追記（同日）: 上限に達したのは、更新の直後の 1 回目だけだった

最初にこの記録を書いたとき、上限に達した理由を「通信の遅さ」と見ていた。変数を 1 つずつ変えて測ると、主な原因は通信ではなく、**ファイルが新しいときの初回の起動の遅さ**だった。

| 測ったもの | 結果 |
| --- | --- |
| 配布物を別の場所へ複製した直後に、入口を直接起動（点検 11 本。GitHub へ問い合わせる 1 本を外した状態） | 4.8 秒（2 回とも） |
| 配布物を、同じ場所から続けて直接起動（同じ 11 本） | 0.8〜1.0 秒（5 回） |
| 点検を 1 本ずつ直接起動 | 1 回目の合計 1.8 秒、2 回目 0.7 秒。どの点検も、1 回目だけ約 0.09 秒遅い |
| **配布した 0.1.5 のまま、Codex の 2 回目のセッション**（点検 12 本。GitHub へ問い合わせる 1 本を含む） | **打ち切りなし。** 3 件の知らせだけが入り、「結果の出ていない点検があります」は入らなかった |

4 行目はセッション `01a0efa6-9fcd-7912-9ec9-959a83fa136a`（2026-09-30 9:11:09 開始。`codex exec -m gpt-5.5 -s read-only` で 1 ターン）。作業場所は 1 回目と同じ。最初のターンの開始（9:11:10）から知らせが入る（9:11:14）までは、約 5 秒だった。

8:57 のセッションは、8:51 に `marketplace upgrade` で 0.1.5 に入れ替えた直後の 1 回目だった。入れ替えでキャッシュのファイルがすべて新しくなり、入口と点検のどれもが初回の起動になった。

初回だけ遅い理由そのものは、確かめていない（macOS が、新しい実行ファイルを初めて起動するときに検査するため、と推定している）。

### この結果から決めたこと

**0.1.6 は出さない。** GitHub へ問い合わせる点検を入口から外す案を、いったん実装まで進めたが、取りやめた。

- 外しても、更新の直後の 1 回目は防げない（通信なしの 11 本でも 4.8 秒で、上限の 5 秒にほぼ届く）
- 2 回目からは、外さなくても打ち切られていない
- 外すと、長く止まったままの課題の見張りが、Codex では動かなくなる

起きるのは、版を上げた直後の 1 回だけ。そのとき入口は、設計どおり、動かせなかった点検の名前を知らせる。

## 分かったこと

### 1. 入口は、合計 5 秒の上限に達した

一覧の最後に置いた、GitHub へ問い合わせる点検（`check-blocked-issues-staleness.sh`）が、途中で打ち切られた。入口を直接起動したときは、12 本で 1.8〜3.5 秒だった。Codex から動いたときは、5 秒では足りなかった。

理由は確かめていない。考えられるのは、Codex が SessionStart の hook を同時に動かしていること（同じタイミングで、共通側の 3 本も動く。そのうち `check-branch-pr-status.sh` も GitHub へ問い合わせる）と、GitHub の応答の遅さ。測ったのは 1 回だけ。

（この段落は、最初に書いたときの見立て。後から測ると、主な原因は別だった。上の「追記」を参照）

入口は、設計どおり、打ち切った点検の名前を知らせた。ただし、毎回こうなるなら、**「結果の出ていない点検があります」の知らせが毎回出て、長く止まった課題の点検は一度も結果を出さない**。

### 2. セッションの始まりの hook は、最初のターンを待たせているように見える

記録の時刻からの推定で、hook がいつ動いたかを直接は見ていない。知らせが会話に入るのは、セッションの開始時ではなく、最初のターンの開始の後。入口が上限に達した今回は、その間が長い。

| セッション | 最初のターンの開始 | hook の知らせが入った時刻 | 差 |
| --- | --- | --- | --- |
| `01a0ef5f…`（仕様書 07 の確認。clone） | 7:54:19 | 7:54:21 | 約 3 秒 |
| `01a0ef99…`（今回。入口が上限に達した） | 8:57:03 | 8:57:10 | 約 7 秒 |

推定が正しければ、人が最初の発言を送ってから、モデルが動き出すまでに、この時間が挟まる。入口の上限を上げると、この待ち時間も伸びる。

### 3. 普段の作業場所で動くのは、プラグインの hook だけ

仕様書 07 の実機確認（E-100）と合う。今回の作業場所では、リポジトリの `.codex/hooks.json` の入口は読み込まれず、プラグインの入口だけが動いた。入口の知らせは 1 回だけ入っており、二重には動いていない。

## 確かめられなかったこと

| 項目 | 理由 |
| --- | --- |
| 入口の実際の所要時間 | セッションの記録には、hook ごとの時間が残らない。分かるのは「5 秒の上限に達した」ことと、最初のターンの開始から知らせまでの約 7 秒 |
| 上限に達するのが毎回か、今回だけか | 追記のとおり、2 回目は達しなかった。3 回目以降と、対話 CLI での 2 回目は測っていない |
