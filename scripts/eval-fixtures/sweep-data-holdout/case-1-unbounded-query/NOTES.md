# sweep-data-holdout / case-1: 上限の無い一覧クエリ

**評価専用（held-out）。** このセットを見てプロンプトや探索手順を調整してはいけない。
隔離は `scripts/check-holdout-isolation.test.sh` が機械で見ている。

## 仕込んだ欠陥

認可は正しい（`requireFacilityAccess` を呼び、施設で絞っている）。
欠けているのは**件数の上限**——`.limit()` も `.range()` も無いので、
行がたまるほど 1 回の応答が重くなる。

**認可の欠落を仕込んでいないのが要点。** `sweep-data/case-1` は
「`requireAuth` を呼んでいない」という**分かりやすい**欠陥で、
そこだけを見るように寄っていないかを、この case で測る。

## なぜ実害があるか

このリポジトリでは、データがたまって壊れた事例が**5 回**ある
（拒否記録の山・監査ログ 1,000 行・a11y の件数・利用者一覧の既定ページ長・
統合テストの後片付け漏れ）。いずれも「書いた日には少なかった」ものである。
`escaped-defects.md` の E-022 / E-023 / E-061 / E-062 / E-065 を参照。

Supabase の PostgREST には既定の上限があるので**無制限には返らない**が、
上限に当たった時点で**黙って切り落とされる**——
呼び出し側は「全部取れた」と思って表示するので、
**行が消えたように見える**（もっと悪い）。

## ほかに何が捕まえるか

- `npm run typecheck` / `npm run lint` … **落とさない**
- `scripts/check-query-validation-coverage.test.sh` … クエリ文字列の**検証**を見るもので、
  結果の件数は対象外
- `scripts/check-append-only-log-indexes.test.sh` … 追記専用の**ログ表**が対象。業務表は見ない
- E2E / 統合テスト … 行が少ないうちは通る（**書いた日には落ちない**のがこの型の性質）

つまり **たまるまで誰も気づかない**。だから Sweep が見つけられるかを測る意味がある。
