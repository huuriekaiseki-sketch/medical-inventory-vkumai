# 引き継ぎフォーマット

「できました」で終わる完了報告は禁止。作業完了時（PR本文・セッション終了報告・
`docs/sessions/` への記録のいずれか）は、以下のフォーマットで引き継ぎメモを残す。
確認範囲がAIごとにブレる問題・後任AIがスコープ外を「重大な見落とし」と誤認する問題に加え、
人間レビュアーが「何が変わり、危険度はどれくらいで、どこを見ればよいか」を短時間で判断できない
問題を防ぐ（issue #666）。PRを「コードの置き場」ではなく「変更が安全に価値を出すと説明する
証拠パッケージ」として書く。

```
## 30秒サマリー
- 変更概要:（1行）
- リスク: (低 / 中 / 高)
- 変更領域:（UI / ロジック / DB / RLS など該当するもののみ）
- 証拠状態:（実測◯件 / サンプル・未検証◯件 — 下記00〜05の各証拠が実測かサンプルかを数える）
- 影響範囲:
- ロールバック可能性:

レビューしてほしい点:
1.
2.

## 00 目的・影響範囲・対象外
- 目的:
- 変更範囲:
- 対象外（今回あえて触らない）:
- 作業中に見つけた別件:（スコープ外の問題を見つけたら、その場で直さずissue化し、
  番号をここにリンクする。「このPRが原因の問題」と「元から別に存在した問題」を混同させない）

## 01 画面がどう変わったか（UI証拠）
- 実際のスクリーンショットか、実装前のモック/サンプルかを明記する
- クリックで新しく出るUI（モーダル・パネル等）があれば、クリック前/後の2枚組で示す

## 02 内部でどう守っているか（ロジック証拠）
- 追加・修正したロジック（該当コミット・差分・ファイル:行へのリンク）
- DB制約など、コード以外の裏付けがあれば明記する

## 03 誰が操作できるか（RLS/権限証拠）
- RLS・権限の変更点（実際のmigration/ポリシーへのリンク）
- 他テナントのIDでアクセスし、弾かれることを確認したか:（RLS/facility境界に
  触れた場合は必須。Issue #24再発防止。チェック観点は
  [`../../docs/agents/known-failure-patterns.md`](../../docs/agents/known-failure-patterns.md) 参照）

## 04 どう確認したか（テスト・検証）
- この変更に直接対応するテスト（テスト名で。`npm run ai:check` の実行有無を含む）
- 全体テストの実行結果（実測値。CI実行URL・実行日時・対象コマンドを添える）
- fault injection: 何を壊し、どのテストが失敗し、復旧後どうなったか（実施した場合）
- 上記の各証拠について、実測か図解/サンプルかを明記し、verify-claimsで検証したかを書く
  （検証していない数値を実測のように見せない）

## 05 何かあったらどうするか（観測・ロールバック）
- リリース後に見るログ/メトリクス:
- 異常の判断基準:
- ロールバック手順:

## 後任AIへの注意
- この実装で壊してはいけない前提:
- 似ているが別物の用語:
- 勝手にリファクタしない場所:
```

バグ修正の場合、04は「問題→原因仮説→修正→確認結果→残るリスク」の形式に置き換えてもよい。
全項目を無理に埋める必要はない。UI変更が無ければ01は「対象外」と書き、該当しない証拠区分は
簡潔に省略してよい。

- PR本文経由での引き継ぎ（`gh pr create`/`gh pr edit`）は、Stop hook
  （`scripts/check-handoff-format.sh`、issue #524／新フォーマットへの追従はissue #666）が
  「## 30秒サマリー」「どう確認したか」の見出しの有無を機械検知し、無ければ警告する
  （PRにつき1回・warningのみ。セッション終了報告・`docs/sessions/`経由の引き継ぎは検知対象外）
